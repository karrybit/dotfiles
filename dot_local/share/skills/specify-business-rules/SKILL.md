# 業務規則仕様のレビューと作成

業務規則の仕様が壊れる箇所は決まっている。**同じ語が別のものを指す／規則に名前がなく例外を書けない／条件が重なって帰結が決まらない／空欄が未決定なのか自由なのか判別できない。** この4つに、それぞれ確立した規約を当てる。

引数: `$ARGUMENTS`（モードとファイルパス。未指定ならユーザーに確認する）

## 4つの規約は重複しない

| 軸 | 規約 | 規定する対象 | reference |
| --- | --- | --- | --- |
| 事実の粒度 | ORM | 規則が乗る事実の単位 | [orm-fact-types.md](references/orm-fact-types.md) |
| 語彙の表記と帰結の様相 | SBVR | 用語の書き方、義務／禁止／許可／必然 | [sbvr-vocabulary.md](references/sbvr-vocabulary.md) |
| 前提と契機の構造 | EARS | 規則が発火する条件 | [ears-patterns.md](references/ears-patterns.md) |
| 規則間の優先関係 | Catala | 原則と例外の解決順序 | [catala-default-logic.md](references/catala-default-logic.md) |

EARS は `shall` 一種類しか持たず様相を区別しない。SBVR は様相を4種に分けるが契機の構造を規定しない。**どれかを落とすとその軸が無規定になる。** 装飾ではなく分担である。

## 入力に形式を要求しない

既存のストーリーやユースケースは書き方が統一されていない。ICONIX や RDRA のような型はあるが、律儀に守られているとは限らない。**だから固定形式を入力要件にしない。** 形式は正規化の出力先である。

```
原文（書かれたまま。変更しない）
  ↓ 正規化（用語・規則・フロー・未決定に割り当てる。原文への参照を保つ）
指摘（ユーザーが読む）
```

**正規化できないことが欠陥である。** どの種別にも割り当てられない文が出たら、それが指摘になる。手順と割り当て表は [normalization.md](references/normalization.md)。

正規化層に置く成果物は3つ。**語彙リストが最初に来る**（層の依存順序）。

| 成果物 | 中身 |
| --- | --- |
| 語彙リスト | 用語・定義・事実型。ORM/SBVR の規律に従う |
| 規則リスト | 名前付き規則と例外関係 |
| 未決定リスト | 3分類・オーナー付き。**指摘の持ち越し先でもある** |

**形は [spec-format.md](references/spec-format.md) の対応する節をそのまま使う。** 3節そろえる必要はなく、`## 語彙` だけのファイルは正当な成果物で、そのまま `check-spec.py` を通る。各レコードに `出典` を書いて原文へ辿れるようにする（lineage）。

`review` で語彙リストだけを作り、`consolidate` に進まない——これは正常な終わり方である。

## モードを決める

| 引数 | 用途 | 形式 |
| --- | --- | --- |
| `review`（既定） | 既存の記述をレビューする | **要求しない** |
| `interview` | ふんわりしたストーリーから規則を引き出す | **要求しない** |
| `consolidate` | 散在した規則を1箇所の正本に集約する | 固定形式（下流・任意） |

`review` と `interview` は `consolidate` を前提にしない。集約するかは別の判断である。

**語彙リストの作成は独立したモードにしない。** 3モードすべての最初の産物であり、取得方法が違うだけである（`review` は既存記述から導出、`interview` は聞き出す）。層の依存順序から外せないため、別skillにも切り出さない。

## review

### 1. スキャン（形式不要・止めない）

```sh
python3 <skill>/scripts/scan-prose.py --ref-pattern 'US-\d+' <ファイル...>
```

原文にそのまま当たる。**ヒットは正常であり、門番ではない。** 隠れた例外語・曖昧語・法令用語・未帰属の空欄・外部への委譲・数量の曖昧・未解決の ID 参照を、行番号と引用付きで返す。

いちばん効くのは**隠れた例外**（「原則として」など）で、原則を名指しせずに例外の存在を示している箇所を指す。ここに続く例外が書かれていないことが多い。

結果は次の段の入力ではなく、**統合段で照合する材料**として持つ。プローブには渡さない。

### 2. プローブA・B（並列）

2つを**並列に、互いにブラインドで**起動する。渡すのは下のプロンプトと対象ファイルのパスだけ。

**渡してはいけないもの**: なぜその仕様を書いたか、どんな議論を経たか、書き手の意図、関連システムの事情、スキャンの結果。渡すと引きずられて検出が落ちる。

#### プローブA: 決定表

```
あなたはこの文書を初めて読む実装者です。書かれた経緯や背景は与えられません。

対象: <ファイルの絶対パス。複数あればすべて>

## やること

1. 文書全体を読み、「条件と、常に成り立つ帰結」を述べている文を拾う。特定の
   1ケースの入出力を述べた例（シナリオ）は、規則とは別に分けて記録する。
2. 拾った規則が参照している条件（金額、区分、状態、有無など）を洗い出す。
3. 各条件の取りうる値を、文書に書かれている範囲で確定する。**書かれていない値を
   補わない。** 値の集合が文書から決まらない条件は、表に入れずに「値域が不明」と
   して報告する。
4. 値が確定した条件の組合せを表にする。組合せが多いときは、各条件の真と偽および
   境界値を1回は含むように行を選び、選んだ理由を書く。
5. 各行について、文書だけを根拠に帰結を1つ決める。
6. 決められなかった行を報告する。

## 報告のしかた

各行を3つに分類する。

- 決定できた: 帰結と、根拠にした文の引用（または行番号）
- 帰結が0個: どの規則も当たらない
- 帰結が2個以上: 複数が当たり優先が決まらない。当たった文をすべて引用する

帰結が0個または2個以上の行を最も重視する。

あわせて次を報告する。

- 例（特定の1ケース）しか書かれておらず、規則が書かれていない箇所。境界値が
  文書から決まらないものはここに入れる。
- 値域が不明で表に入れられなかった条件。

- 文書に書かれていないことを補って決めない。決められないならそう書く。
- 外部の資料や、業務についての一般知識で埋めない。
- 順序を前提にした手順（フロー）は規則として扱わない。除外したことだけ書く。
- ファイルを変更しない。報告のみ。
- 追加の質問はせず、1回で完了する。
```

#### プローブB: 語彙

```
あなたはこの文書を初めて読む読者です。書かれた経緯や背景は与えられません。

対象: <ファイルの絶対パス。複数あればすべて>

## やること

1. 文書を読み、業務上の概念を指している語を出現順に列挙する。各語が何を指すかを
   文書の記述だけから推測して書く。推測できないものは「文書から決定できない」と
   書く。
2. 1 を書き終えてから、文書内に用語集・ドメインモデル・概念モデルに相当する記述
   があるかを探し、自分の一覧と突き合わせる。なければ「存在しない」と記録する。

## 報告のしかた

- 同じ語が、箇所によって別のものを指していると読める（引用を2つ以上挙げる）
- 別の語が、同じものを指していると読める（表記ゆれ）
- 用語集の定義と、本文での使われ方が食い違う
- 用語集にあるが、本文で一度も使われていない

最初の2つを最も重視する。

- 重要でないものは報告しない。0件でよい。無理に指摘を作らないこと。
- 多くても5件。影響の大きい順に並べる。
- ファイルを変更しない。報告のみ。
- 追加の質問はせず、1回で完了する。
```

プローブBが**本文を先に読み、用語集を後で探す**のは意図的。宣言された用語集を先に見ると、それに合わせて読んでしまい、乖離が見えなくなる。

### 3. 統合

統合は自動化せず、本体セッションが行う。

- 各指摘を採用・却下し、**却下したものには理由を持つ**。統合の役割は発見ではなく偽陽性の除去である。
- **スキャンの結果とプローブの指摘を突き合わせる。** スキャンが「原則として」を挙げた箇所で、プローブAが帰結2個以上を報告していたら、それは同じ欠陥の2つの現れ方であり優先度が高い。
- **決定できなかった箇所を3分類に振り分ける。**

| 分類 | 意味 | 実装を止めるか | 書くべきこと |
| --- | --- | --- | --- |
| 未決定 | 業務判断がまだ存在しない | 止める | 決める人、決まらないと何が書けないか |
| 書き忘れ | 判断済みだが記録が欠けている | 止めない | 誰に聞けば埋まるか |
| 意図的自由 | 委ねることが設計 | 止めない | **誰の自由か**と**何が境界か** |

- **この3分類をプローブ側のプロンプトに書いてはいけない。** 「空欄は意図的かもしれない」と伝えると報告そのものが抑制され、本当の書き忘れも出てこなくなる。
- 帰結が2個以上の行は、どちらを優先するかが業務判断なので、決まらないなら `未決定` に立てる。
- **プローブBの用語一覧を語彙リストとして残す。** 指摘を捨てても語彙リストは残す。次のレビューの出発点になる。
- 直すかどうかは「直すか残すか」へ。

## interview

ふんわり伝えられたユーザーストーリーを受け、4軸で未決定な箇所を1問ずつ聞く。質問カタログと回し方は [interview.md](references/interview.md)。

1. 伝えられた内容を、**語彙・規則・例・フロー・未決定**に仮に振り分ける（[normalization.md](references/normalization.md) の割り当て表）。
2. 振り分けられなかった箇所と、振り分けたが決まっていない箇所を、聞く候補にする。
3. **1問ずつ聞く。推奨案を添える。** 既出の情報や既存文書・コードから導ける答えは聞かない。
4. 「分からない」と返ってきたら**追撃せず**、未決定レコードに落として次へ進む。業務判断が存在しないものは聞き方を変えても出てこない。
5. カタログを順に歩かない。聞くのは実際に未決定な箇所だけ。
6. 終わったら「直すか残すか」へ。

一問一答のインタビューは一般的な手順で、同種の手順を持つ skill が環境に併存することがある。**それでも依存にせず、規律をこのskillに書く。** Claude Code に skill 間の依存機構はなく、このskillは明示呼び出し専用なので、別の skill が同時に読み込まれる保証がない。発火しないと黙って劣化するものを依存にしてはいけない。

**既存の用語集がある場所を拡張し、競合する語彙リストを新規に作らない。** 2つできた時点で、このskillが検出しようとしている乖離を自分で作ることになる。統合できないなら「既存文書との統合が必要」を未決定レコードに立てる（[interview.md](references/interview.md)）。

最も生産的な2問。

- **その規則が当てはまらないケースはありますか** — ふんわりした説明はほぼ常に原則だけを述べ、例外は聞かれるまで出てこない
- **それを破ったらどうなりますか** — 義務（違反を検出し対処する）か必然（破れない、定義）かを分ける

## 直すか残すか

**規模で挙動を切り替えない。常にリストを先に書き、それから適用を問う。** リストは記録として必要であり、適用するかどうかとは別物である。

判定するのは行数やファイル数ではなく、**ユーザーが下さなければならない決定の数**である。修正が不可能になる理由は編集量ではなく、何を取り入れて何を捨てるかの判断が追いつかなくなることだから。

| 例 | 決定数 |
| --- | --- |
| 「申請／経費申請／精算申請」を「申請」に統一する（影響50箇所） | **1** |
| 8,000円の出張申請でどちらの規則が勝つかを決める | 1 |
| 自動承認の閾値の境界値を決める | 1 |
| ある例外の親をどの規則にするかを決める | 1 |

決定後の機械的な波及は数えない。**1つの語彙決定が50箇所の編集を覆う**ため、編集量で測ると規模を過大に見る。

| 決定数 | 進め方 |
| --- | --- |
| 10件以下 | リストを出し、その場で1件ずつ確認して直す |
| 11件以上 | リストのまま渡す。**この場では直さない。** 優先順位を付けて別の回に分ける |

10件は暫定値。単一ファイルの行数では測らない——**ファイル群全体で数える。**

どちらの場合も、直さなかったものは**未決定リストに落とす**。新しい仕組みを作らない。[spec-format.md](references/spec-format.md) の未決定レコード（`分類` / `オーナー` / `対象` / `内容`）がそのまま持ち越しの器であり、`check-spec.py` が分類とオーナーの欠落を検査する。**オーナーのない持ち越しは作らせない。**

**進行中案件の原文を書き換えない。** 直すのは正規化層のファイルである。チケットや Confluence ページに触るかはチームの判断であり、このskillの範囲外。

## consolidate

散在した規則を1箇所の正本に集約すると決めたときだけ走らせる。

1. [normalization.md](references/normalization.md) の割り当て表で、原文から用語・規則・未決定を導出する。**原文は変更せず別ファイルに作る。各レコードに `出典` を書く。**
2. [spec-format.md](references/spec-format.md) の形式で書く。層の順序を守る（語彙 → 規則文 → 命名 → 例外構造 → 未決定）。**命名は Catala の要求**——参照先に ID がなければ `例外元` が書けず、原則と例外を表現できない。パターンは宣言せず規則文から導出されるので、**パターンを先に決めてから文を書く**（欄はないが規律は残る）。
3. 例外構造を組む。兄弟（同じ親を持つ例外）が2つ以上できたら、**その場で条件が排他かを確かめる**（[catala-default-logic.md](references/catala-default-logic.md)）。通した例は [worked-example.md](references/worked-example.md)。
4. 検査する。エラー0件になるまで直す。

```sh
python3 <skill>/scripts/check-spec.py <正規化したファイル...>
```

作成の直後に `review` のプローブを続けて走らせない。自分が書いたものを同じセッションで読み直すのは自己レビューであり、効果がないことが測定されている（[evidence-basis](../review-doc-fresh-eyes/references/evidence-basis.md)）。

## 適用範囲

文書の種類ではなく、**文書のどの部分か**で切れる。

| 層 | ユーザーストーリー | ユースケース |
| --- | --- | --- |
| 語彙（ORM/SBVR） | ◎ 散在するほど効く | ◎ |
| EARS | △ **受入基準にのみ** | ✕ フロー手順には効かない |
| Catala | △ **抽出した規則にのみ** | ✕ 例外フローとは別物 |
| 未決定の3分類 | ◎ 意図的に不完全なので効く | ○ |

押し込んではいけない2箇所。

- **ストーリー文（「〜として、〜したい」）とフロー手順を EARS 化しない。** 前者は目標と理由の記述で、契機に対する応答ではない。後者は順序の中の1段であり、EARS には順序の概念がない。「手順3」を EARS で書くと「手順2の後」を契機に埋め込むことになり、それは記法が合っていない合図である。
- **「例外フロー」と Catala の「例外」は別物。** 例外フローは制御がどこへ分岐するか（順序）、Catala の例外は重なる条件でどの規範が値を決めるか（優先）。混同すると優先でない情報を優先として符号化する。

**ユースケースのフローは `review-doc-fresh-eyes` の「手順の文書」型へ別便で回す。** このskillのプローブに3体目として足さない。

## 守る制約

- **スキャンで止めない。** 既存文書にヒットが出るのは正常。件数を欠陥数と読み替えない。
- **プローブを3体目に増やさない。** 3体目以降の追加検出はほぼなく、観点を分けても同じ欠陥を見つけることが測定されている。増やすなら、それが本当に別のものを拾うかを実測してから。
- **反復させない。** 1文書につき各プローブ1回。ラウンドを足すと真陽性はほとんど増えず偽陽性が増える。
- **「必ず指摘せよ」と要求しない。** 0件は正常な結果。
- **`interview` や `consolidate` の直後に `review` のプローブを走らせない。** 自分が引き出した・書いた内容を同じセッションで読み直すのは自己レビューであり、効果がないことが測定されている。日を分けるか別セッションで走らせる。
- **オーナーのない持ち越しを作らない。** 直さずに残すものには必ず分類と決める人を付ける。付けられないなら、それを付けることが最初の決定である。
- **`review-doc-fresh-eyes` と1つの段にまとめない。** あちらは文書としての伝わりやすさを見る手順で、目的が違う。順に、別の作業として走らせる。
- 各制約の根拠は [evidence-basis](../review-doc-fresh-eyes/references/evidence-basis.md) にある。設定を変える前に読む。

## 非目標

- **コンパイラではない。** Catala は実在の言語だが、ここでは自然言語仕様の設計規律として構造だけを借りている。実行・検証したいなら本物の Catala かルールエンジンへ渡す。
- **網羅性を保証しない。** 決定表が埋まっても、条件として洗い出されなかった軸の穴は見えない。
- **全件を正規化しない。** 1つの業務規則を疑ったら、それに触れている記述だけを集める。
- **費用が仕様の価値を超えないこと。** スキャンだけ走らせて終える判断でよい。

## 記録と見直し

3回使うまでは暫定として扱う。毎回、スキャンの件数、プローブの指摘件数と採用件数、**決定数と実際に直せた件数**、所要時間をユーザーに報告する。3回溜まったら**プローブの体数・上限件数・スキャンの語彙一覧・決定数の閾値（10件）**を見直す。

決定数の閾値はとくに根拠がない。実測で置き換える対象である。11件以上でも直せたなら上げ、10件でも判断が追いつかなかったなら下げる。

検出規則を変えたら自己検証を走らせる。スクリプトと reference が片側だけ変わっていると落ちる。

```sh
python3 <skill>/scripts/scan-prose.py --selftest
python3 <skill>/scripts/check-spec.py --selftest
```

根拠があって動かさないのは「原文を変更しない」「正規化できないことを欠陥として扱う」「例と規則を区別する」「プローブに経緯を渡さない」「3分類を統合段で行う」の5点である。
