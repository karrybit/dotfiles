# 仕様ファイル形式（正規化の出力先）

Last checked: 2026-08-06

`scripts/check-spec.py` が検査できる最小の固定形式。

**これは入力要件ではない。正規化の出力先である。** 既存のストーリーやユースケースをこの形式で書き直すことを求めていない。進行中の案件の記述は形式が統一されておらず、今後も統一されない。原文はそのまま残し、正規化した結果をこの形式で**別ファイルに**作る（`references/normalization.md`）。

したがってこの形式が要るのは `consolidate` モード——散在した業務規則を1箇所に集約すると決めたときだけである。`review` モードは形式を要求しない。

形式は機械チェックのために存在し、それ以上の意味はない。人が読む順序（語彙 → 規則 → 未決定）と、依存の順序を一致させてある。

## 全体構造

見出しは3つ。順序も固定する。

```markdown
# <仕様名>

## 語彙

### <用語>

- 種別: 実体 | 値 | 事実型
- 定義: <一文>
- 出典: <原文の所在。任意>

## 規則

### BR-<AREA>-<NNN> <規則名>

- 例外元: なし | BR-<AREA>-<NNN>
- 規則: <日本語 EARS 文>
- 出典: <原文の所在。省略すると警告>

## 未決定

### UD-<NNN>

- 分類: 未決定 | 書き忘れ | 意図的自由
- オーナー: <名前または役割>
- 対象: BR-<AREA>-<NNN> | 語彙:<用語>
- 内容: <何が決まっていないか>
```

3つの節がすべて必要なわけではない。**`## 語彙` だけのファイルは正当な成果物**であり（`review` モードの語彙リスト）、そのまま検査を通る。規則が1件もないときは「どの規則からも参照されていない」警告を出さない。

## パターンは宣言しない

EARS のパターンを書く欄はない。**規則文のキーワードから導出する。**

欄を置くと同じ情報を2箇所に書かせることになり、検査は両者の照合しかできない——欄そのものが情報を持たない。

```
（キーワードなし）        → 常時
「間、」                  → 状態
「とき、」                → 契機
「構成では」              → 構成
「ならば、」              → 逸脱
「間、」＋「とき、」      → 複合
上記以外の組合せ          → 複合(状態+逸脱) のように内訳を表示
```

**組合せはエラーにしない。** EARS 原典 §4.7 は When / While / Where の組合せを認め、さらにそれらを If-Then 内で使うことを明示している（`references/ears-patterns.md`）。**導出は分類であって検査ではない。**

検査結果には導出したパターンと様相の内訳が出る。意図と違っていたら規則文を直す。

**パターンを先に決めてから文を書く**規律は残る（`SKILL.md`）。それは手順の指示であって、ファイルのフィールドである必要はない。

## 様相は2系列×3

規則文は次の6つのいずれかで終える。系列をまたぐ取り違えが意味を変える（`references/sbvr-vocabulary.md`）。

| 系列 | 様相 | 固定形 |
| --- | --- | --- |
| 行動的（破れる） | 義務 | 「〜しなければならない」 |
| | 禁止 | 「〜してはならない」 |
| | 許可 | 「〜してよい」 |
| 定義的（破れない） | 必然 | 「〜である」 |
| | 不可能 | 「〜ことはない」 |
| | 可能 | 「〜しうる」 |

**許可・可能は条件が必須。** 無制限の許可は SBVR では規則ではなく advice にあたる（「No business rule is an advice.」）。条件は EARS のキーワードで表れるので、キーワードを1つも持たない許可・可能はエラーになる。

```markdown
❌ - 規則: [経理部] は [申請] を 承認 してよい
✅ - 規則: [申請] が [出張] に 紐づく 間、[経理部] は [申請] を 承認 してよい
```

## 出典（lineage）

原文から正規化したレコードには `出典` を書く。行番号、チケット ID、引用のいずれでもよい。

```markdown
- 出典: stories.md:17 US-1355「原則として上長承認が必要」
```

`references/normalization.md` の3層構成は各レコードが原文へ辿れることを要求している。**`出典` がその場所である。** 規則に `出典` がないと警告が出る（新規に起草したものなら無視してよい）。

## 検査の抑制

出典の文言をそのまま保つ必要があるなど、検査に逆らう正当な理由があるときは抑制する。**コードと理由の両方が必須。**

```markdown
- 規則: [申請] が却下された場合、[経費精算システム] は 通知 しなければならない
- 許容: E212 出典（経費規程第12条）の文言をそのまま用いる
```

複数行書ける。**理由のない抑制は認めない**（`許容: E212` だけではエラー）。理由なしの抑制は穴だが、理由付きは記録された判断である。

抑制が何も抑制していない場合は警告が出る。指摘が解消したら行を消す。

## 用語の角括弧

規則文と事実型の中で、語彙に定義した用語は `[顧客]` のように角括弧で囲む。

これは SBVR が term / Name / verb / keyword をフォントで区別しているのを、プレーンテキストで代替したもの。SBVR Structured English は**規格上は非規範**（Annex A は informative）なので、代替が許される。意図は「規則文のどの語が定義済み概念か」を見た目で判別可能にすることなので、書体の代わりに区切り記号を使う。**囲まれた語が語彙節にないと第0段が落ちる**ため、語彙と規則の乖離が機械的に検出できる。

囲む対象は名詞概念・個体概念に加え、**動詞概念語法**も含む（SBVR では語彙エントリの primary representation は designation または verb concept wording）。

囲まないもの: 数値、単位、日付、`しなければならない` などの様相語、EARS のキーワード。

## 事実型の書き方

`種別: 事実型` の語彙項目には `- 事実型:` 行を足し、ORM の読み下し形式で書く。

```markdown
### 発注

- 種別: 事実型
- 定義: 顧客が申請を提出する関係。
- 事実型: [顧客] は [申請] を 提出する
```

## ID 規約

| 種別 | 形式 | 例 |
| --- | --- | --- |
| 規則 | `BR-<AREA>-<NNN>` | `BR-EXP-010` |
| 未決定 | `UD-<NNN>` | `UD-003` |

`<AREA>` は英大文字とハイフンのみ。`<NNN>` は3桁以上の数字。

**ID は再利用しない。** 規則を削除しても番号を空けたままにする。例外は参照先の ID が存在することを前提にしており、ID を再利用すると過去の参照が別の規則を指す。

番号は10刻みで振る（`010`, `020`）。あいだに規則を挿入するときに全体を振り直さずに済む。

## 複数ファイルに分けるとき

規則が増えたら `## 規則` を領域ごとのファイルに分割してよい。ただし**語彙は1ファイルに保つ**。語彙が分かれると同じ用語が別々に定義され、SBVR/ORM を使う理由そのものが失われる。

スクリプトは複数ファイルを引数に取り、語彙を統合してから検査する。

```sh
python3 scripts/check-spec.py 語彙.md 規則-経費.md 規則-与信.md
```

## 検査規則そのものを変えるとき

日本語の固定形・禁止語・様相の一覧を変えたら、変更後に自己検証を走らせる。

```sh
python3 scripts/check-spec.py --selftest
```

各パターンの正例と、検出したい違反1件ずつを埋め込んで検査してある。**固定形を変えて `--selftest` が落ちたら、スクリプトと reference のどちらかが片側だけ変わっている。** `references/ears-patterns.md` の検査キーワード表と、`SELFTEST_CASES` を同時に直す。

## Practical Use

- 既存の仕様をこの形式へ移すとき、まず語彙節だけを作って第0段を通す。規則を全部書いてから形式を直すと手戻りが大きい。
- 形式が窮屈で書けない箇所が出たら、それは形式の不足ではなく**規則が elementary でない**可能性を先に疑う。`references/orm-fact-types.md` を読む。
- この形式は仕様の最終成果物である必要はない。読み手向けの文書は別に書き、この形式を検査可能な正本として保つ運用でよい。

Revalidation trigger: 第0段のチェックを追加または削除したとき。仕様を複数ファイルに分けた運用を実際に始めたとき。
