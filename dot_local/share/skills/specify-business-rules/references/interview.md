# インタビューで規則を引き出す

Last checked: 2026-08-06

ふんわり伝えられたユーザーストーリーから、4軸で未決定な箇所を特定して聞き出す。**このファイルの実体は質問カタログである。** 何を聞くかが4つの規約から導かれることに価値がある。

## 自己完結させる

一問一答のインタビューは一般的な手順で、同種の手順を持つ skill が環境に併存することがある。**それでもこのskillは自己完結させる。重複は受け入れる。**

- Claude Code に skill 間の依存機構がない。詳細を持つ支持された方法は、その skill 自身の `references/` に置くこと（progressive disclosure）である。
- このskillは `disable-model-invocation: true` で明示呼び出し専用。ユーザーが明示的に呼んだ瞬間に別の skill も同時に読み込まれることは、どこにも保証されていない。
- skill は確率的に発火する。発火しないと手順が黙って劣化するものを依存にしてはいけない（`manage-agent-skills`）。インタビューの規律が読み込まれなければ、質問を一度に並べる形へ静かに退化する。

したがって下の規律は、他に同種の skill があっても**ここに書く**。

## 回し方

- **1問ずつ。** 回答を待つ。まとめて出さない。
- **推奨案を添える。** 「どちらですか」だけでは答えにくい。
- **答えが既出の情報・既存文書・コードから導けるなら聞かない。** 調べる。
- **依存順に聞く。** 決定には依存関係があり、順序を守らないと答えが無駄になる。`語彙 → 規則文 → 命名 → 例外構造` の順（`SKILL.md` の層の依存順序）。**例外の優先を先に聞いても、語彙が動けば答えが変わる。**
- **既存の実装と突き合わせる。** 進行中案件では、語られた内容と動いているコードが食い違うことがある。見つけたら聞く。「いま実装は X ですが、説明は Y でした。どちらが正ですか。」
- **用語集と食い違ったら即座に指摘する。** 後でまとめて出さない。その語を使ったまま進むと、以降の回答すべてが曖昧なまま積み上がる。
- **カタログを順に歩かない。** 聞くのは、実際に未決定な箇所だけ。全問を機械的に消化すると、決まっていることを聞き直して時間を使う。
- **「分からない」は正当な終点。** 追撃しない。未決定レコードに落として次へ進む。業務判断が存在しないものは、聞き方を変えても出てこない。

## 質問カタログ

### 事実の粒度（ORM）

| 聞くこと | 何を決めているか |
| --- | --- |
| その実例を1件、具体的な数字と名前で挙げてください | CSDP step 1。抽象論から実例へ落とす |
| それは「AがBをCする」に分解できますか | elementary fact かどうか |
| 分解すると失われる意味はありますか | 分解すべきか否か |
| その項目が空のまま存在することはありますか | 属性に潜む別の事実型 |

最後の質問が効く。「金額未入力の申請はありえますか」に「ある」と答えたら、金額と申請は別の事実である。

### 語彙と様相（SBVR）

| 聞くこと | 何を決めているか |
| --- | --- |
| その語は、別の場面で別の名前で呼ばれていませんか | 表記ゆれ |
| **それを破ったらどうなりますか** | 義務か必然か |
| 破れないなら、それは定義ですか | 必然の確認 |
| 書かれていない行為は許されますか、禁じられますか | 許可規則を置くべきか |

**「破ったらどうなりますか」が最も生産的。** 「何も起きない、破れない」なら必然（である）。「違反として検出し対処する」なら義務（しなければならない）。ここを間違えると、存在しない違反への対処を実装するか、違反検出が仕様から落ちる。

### 前提と契機（EARS）

| 聞くこと | 何を決めているか |
| --- | --- |
| それには終わりがありますか | 状態か契機か |
| 正常な流れですか、望まない事象ですか | 契機か逸脱か |
| 実行中に変わりますか、契約やビルドで決まりますか | 状態か構成か |
| その条件が続くあいだ、何度でも成立しますか | 状態の確認 |

「〜の場合」と言われたら、この4つのどれなのかが決まっていない。日本語では区別が表層に出ないので、必ず聞く（`references/ears-patterns.md`）。

### 規則間の優先（DMN / Catala）

| 聞くこと | 何を決めているか |
| --- | --- |
| **その規則が当てはまらないケースはありますか** | 例外の存在 |
| 「原則として」と言いましたが、例外は何ですか | 隠れた例外 |
| 2つの条件が同時に成立したら、どちらが勝ちますか | 兄弟の排他性 |
| その例外は、どの規則の例外ですか | 木の親 |
| どの条件にも当てはまらない入力では何が起きますか | 原則の欠落 |

**「その規則が当てはまらないケースはありますか」が単独で最も生産的な質問。** ふんわりした説明はほぼ常に原則だけを述べ、例外は聞かれるまで出てこない。

3番目は**具体値で聞く。** 「8,000円の出張申請ではどうなりますか」のほうが「条件が重なったらどうしますか」より答えが出る。抽象的に聞くと抽象的に答えられ、境界が決まらない。

### 未決定の3分類

未決定が見つかったら、分類そのものを聞く。**推測しない。**

> それは (a) まだ決まっていない / (b) 決まっているが書いていない / (c) 意図的に委ねている、のどれですか。

- (a) なら: 誰が決めますか。決まらないと何が書けませんか。
- (b) なら: 誰に聞けば分かりますか。
- (c) なら: **誰の自由ですか。境界は何ですか。**

(c) で境界を答えられないなら、それは意図的自由ではなく (a) である。「実装に委ねる」と言いながら許容範囲を言えないのは、まだ決めていないだけ。ここを詰めないと、後で「そんな実装は想定していない」になる。

## 例と規則を取り違えない

ふんわりした説明は例で語られる。「8,000円の申請を出したら自動で通ってほしい」は例であり、規則ではない。

> その 8,000 円が 12,000 円だったらどうなりますか。境界はどこですか。

例しか得られていない状態で規則を書くと、閾値を勝手に決めることになる。**境界は書き手にしか埋められない。** 答えが出ないなら未決定に落とす（`references/normalization.md`）。

## 既存の用語集と共存する

リポジトリに既に用語集・ドメインモデル・概念モデルに相当する文書があるなら（名前は何でもよい）、**そこを拡張する。競合する語彙リストを新規に作らない。**

語彙リストが2つできた時点で、このskillが検出しようとしている乖離を自分で作ることになる。**自己矛盾であり、これは守る制約である。**

既存文書を書き換える権限がない、または対象範囲が違うなら、語彙リストは作ってよい。ただし**「既存の（その文書）と統合が必要」を未決定レコードに立てる。** 黙って2つ目を作らない。

## 終わり方

次のすべてが揃ったら終える。揃わないものは未決定レコードになる。

- 語彙: 出てきた概念すべてに定義があり、表記ゆれが解消されている
- 規則: 各規則にパターンと様相がある
- 命名: 各規則に ID がある
- 例外: 各規則の親が決まり、兄弟が排他である
- 未決定: すべての空欄に3分類とオーナーがある

**全部埋まるまで続けない。** 埋まらないと分かった時点で未決定に落として終える。インタビューの目的は完成ではなく、**何が決まっていないかを確定させること**である。

## Practical Use

- 聞いた結果は、その場で書くか未決定レコードに残すかをユーザーに選ばせる（`SKILL.md` の「直すか残すか」）。
- 1回で扱う規則は少なくてよい。1つの業務規則の原則と例外が固まれば十分な成果。
- インタビュー直後に `review` のプローブを走らせない。自分が引き出した内容を同じセッションで読み直すのは自己レビューになる。

Revalidation trigger: Claude Code に skill 間の依存機構が入ったとき（自己完結の判断を再検討する）。実際にインタビューを3回行い、カタログの質問が足りたかを確認したとき。
