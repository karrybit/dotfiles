# 並行実行可能なタスクへの分解

入力: `$ARGUMENTS`（未指定なら、対象のファイルか Issue 番号をユーザーに確認する）

目的は優先順位を付けることではなく、**同時に着手しても互いを壊さないタスクの集合を作ること**。
そのため分解の判定基準は「小さいか」ではなく「独立しているか」に置く。

## この手順の要点

- **ファイル衝突は独立性の反証として扱う。** 同じファイルを触る2タスクは、依存を書き足して
  済ませるのではなく、分解し直すか直列化する。
- **3つの尺度はラベルではなく行動の引き金。** 値が決まった時点で次にすることが決まる。
  引き金が引けない尺度は付けても意味がないので、下の表以外の軸を増やさない。
- **出力は再構築可能にする。** `生成元` を必ず記録する。この markdown は Issue と元メモから
  導出された派生物で、唯一の真実の源ではない。

## 1. 入力の取り込み

| 入力 | すること |
| --- | --- |
| 既存の未構造メモ | 全文を読み、**書かれている情報を1つも捨てずに**スキーマへ移す |
| Issue 番号群 | `gh issue view <n>` で本文とコメントを読み、変更対象を列挙する |
| 出力先に既存ファイルがある | 読んでから更新する。新規作成で上書きしない |

**未構造の入力ファイルを書き換えない。** 出力先は固定（段4）なので入力と衝突しないが、
「構造化したので元は不要」と判断して消したり移したりもしない。元メモは、3軸の判定やローカル
分割の切り方が妥当だったかを後から検算する唯一の材料で、gitignore された場所にあれば git
履歴からも復元できない。

未構造メモから移すとき、落としやすいのは次の4種。スキーマに受け皿があるので必ず拾う。

- リポジトリ固有の運用ルール（CI の確認方法、既知の lint 制約、サンドボックスの制約）
- ファイル衝突のホットスポット
- 未 Issue 化の検討事項
- 親 / トラッキング Issue と、その子の対応

移し先はいずれも下の出力スキーマに同名の節がある。行き場のない情報が出たら、捨てずに節を足す。

ただし「1つも捨てない」は記述の忠実性についての原則で、**認証情報・トークン・秘密値・
セッション状態は例外**。Issue 本文や元メモに書かれていても持ち込まない。忠実性はそれらを
写す理由にならない。

## 2. 3つの尺度

| 軸 | 値 | 判定基準 | 引き起こす行動 |
| --- | --- | --- | --- |
| 影響度 | S | 単一ファイル / 単一コンポーネント内 | — |
| | M | 1コンポーネント内。呼び出し側の変更は不要 | — |
| | L | 公開インタフェース（入力、名前、パス、データ形式）が変わる、または外部リポジトリからの呼び出しに影響する | **`gh search code` で外部の呼び出し箇所を確認する。** 削除や改名を含む場合は、着手直前に取り直す（検索はインデックスベースで遅延がある） |
| 作業量 | S | 1PR で完結する | — |
| | M | 1〜2PR。1タスクとして許容する | — |
| | L | 3PR 以上 | **ローカル分割が必須。** 子タスクへ割るまで着手可能にしない |
| 重要度 | 高 / 中 / 低 | 他タスクを解錠するか、ロードマップ本線か、外部の返答待ちが挟まるか | 根拠付きで提案し、**決めるのはユーザー**。エージェントが確定させない |

作業量 L のまま残っているタスクは、この手順の失敗を意味する。子タスクへ割ってから次へ進む。

## 3. 依存とファイル衝突

3種を区別する。混ぜると直列化しすぎて並行の余地が消える。

| 種類 | 判定 | 扱い |
| --- | --- | --- |
| 順序依存 | B は A がマージされないと成立しない | 直列鎖に置く。依存は B 側にだけ書く |
| ファイル衝突 | A と B が同じファイルを触る | **独立していない証拠。** 分解し直す、直列化する、または「表の1行追加に留める」等の回避策を明記した上で同時進行を許す |
| 意味依存 | 同じ設計判断を2箇所で決めることになる | 片方に寄せる。判断だけの独立タスクは作らない |

回避策付きで同時進行を許すのは、衝突が機械的に解決できると言える場合に限る。言えないなら
直列化する。

並行可能集合は波として示す。第1波は依存を持たないタスク全部、第2波はその完了で解錠される
タスク。人数や担当を前提にしない。

**波はファイルに書かない。** 依存欄と現在の PR 状態から毎回計算できるうえ、何かがマージされる
たびに書き換えが必要になる。聞かれた時点で計算して会話で示す。

## 4. 出力

置き場は作業中リポジトリのルート直下 `.analyze-tasks/backlog.md`。**固定**で、リポジトリごとに
名前を変えない。固定にすることで、次のセッションが探索なしで見つけられ、再実行が新規作成では
なく更新になる。

**ドットを外さない。** 非ドットのルートディレクトリは chezmoi のソースツリーでソースエントリ
として扱われ、`chezmoi apply` で `$HOME` に配備されてしまう。ドット接頭辞はツール所有の状態を
表す慣習（`.git` / `.claude` / `.venv`）でもあり、リポジトリの内容と衝突しない。

**書き込む前に、無視されていることを機械的に確認する。**

```sh
git check-ignore -v .analyze-tasks/backlog.md
```

一致した無視規則を表示して終了コード 0 なら書いてよい。1 が返ったら**書き込まない**。
既定では global の `~/.config/git/ignore` の `/.analyze-tasks/` が一致するので、リポジトリ側の
`.gitignore` に手を入れる必要はない。一致しない環境（global ignore が未配備など）では
`${XDG_STATE_HOME:-$HOME/.local/state}/agents/analyze-tasks/<repo>/backlog.md` に退避する。

この確認は整理のためではなく安全境界のため。このファイルには Issue から写した内部の名前や
URL が入るので、commit される場所には絶対に置かない。

タスク ID は **Issue 番号をそのまま使う**（`#46`）。1つの Issue をローカルで分割した子には
連番を足す（`#44-1` / `#44-2`）。Issue が存在しない作業にだけ `T1` / `T1-1` を使う。

ID が Issue を指すので、ブランチ名と worktree 名からどの Issue の作業かが直接辿れる。ID とは
別に Issue を指したいときだけ `関連:` を足す（他タスクの完了で解消される Issue など）。

````markdown
# <タイトル>

- 生成元: <元ファイルのパス / Issue 番号の列>
- 並行数の上限: 3

## タスク

- [ ] **#46** deploy-status 通知 action を追加する · 影響:S 作業:S 重要:高 · 依存:なし
  - 対象: `actions/notify/deploy-status/**`
  - 検証: `gh pr checks`（actionlint / ghalint / zizmor / pinact）
- [ ] **#44** build-n-push workflow と部品 action を追加する · 影響:L 作業:L 重要:高 · 依存:なし
  - 作業量 L のため子タスクへ分割。#44 自体は着手しない
  - [ ] **#44-1** Secrets Manager 取得 action · 影響:S 作業:S · 依存:なし
    - 対象: `actions/secrets/aws/**`
  - [ ] **#44-2** workflow を合成する · 影響:L 作業:M · 依存:#44-1
    - 関連: #37（この完了で解消する）
    - 影響 L: `gh search code` で外部呼び出しを確認済み（0件、2026-08-16 時点）
- [ ] **T1** lint の既存指摘を棚卸しする（Issue 未作成） · 影響:S 作業:M 重要:低 · 依存:なし

## ファイル衝突ホットスポット

| ファイル | 触るタスク | 回避策 |
| --- | --- | --- |
| `README.md` | #46, #40, #48 | 表の1行追加に留めれば機械的に解決できるので同時進行可 |
| `CONTRIBUTING.md` | #39 のみ | 衝突なし |

## 親 / トラッキング Issue

単独の PR を持たず、子が終わったら閉じる Issue。タスク表には並べない。

| Issue | 追跡対象 | 閉じる条件 |
| --- | --- | --- |
| #34 | #46, #44, #48 | 全部マージ |
| #37 | #44-2 | #44-2 のマージで解消。不採用なら最小対応が別途必要 |

## 対象外・保留

- <スコープ外と判断したものと、その理由>

## 未 Issue 化の検討事項

- <まだ Issue になっていないが記録しておくもの。着手するなら T 番号でタスク表へ>

## このリポジトリ固有の運用ルール

- <元メモから引き継ぐ。捨てない>
````

### 進行状態は保存しない

進行状態・ブランチ名・PR 番号・worktree のパス・並行可能集合は、**すべて git と GitHub から
導出できる**。ファイルに持つと変更のたびに書き換えが必要になり、二重の真実の源になって必ず
ずれる。保存するのは判断と分析の結果だけにする。

| 知りたいこと | 導出方法 |
| --- | --- |
| いま進行中のタスク | `git worktree list`（ディレクトリ名が ID） |
| ブランチ名 | 規約から導く。ID の `#` を外したものが接頭辞 |
| PR 番号と draft / merged | `gh pr list --state all --json number,headRefName,isDraft,state` |
| 並行可能集合 | 依存欄と上の PR 状態から計算する。**波を書き留めない** |
| このファイル自体が陳腐化しているか | `gh issue list --state all --json number,state` と表の ID を突き合わせる。表に無い open Issue、または未チェックなのに closed の Issue があれば作り直す |

最後の行が鮮度の指標。更新日を持たせないのは、知りたいのが経過時間ではなく**導出元が変わったか**
だから。日付より正確で、保存もいらない。

チェックボックスだけは残す。1タスクにつき変わるのは1回（マージ時）だけで、コマンドを打たずに
全体を見渡せる価値が書き換えのコストを上回る。

状態を聞かれたら、ファイルを読むのではなく上のコマンドを叩く。ファイルと git がずれていたら
git が正しい。

## 5. 合意

最初の編集より前に、タスク表と並行可能集合をユーザーに提示して合意を取る。分解の誤りは
実行に入ってからでは巻き戻しが高い。

- 重要度はユーザーが決める。提案のまま確定させない
- 新規 GitHub Issue を作る場合のみ、既存ルールどおりタイトルと境界を先に確認する。
  **ローカル分割だけなら Issue は作らない**
- 実行は `parallel-work` が引き取る。この手順では worktree を作らず、コードも変更しない
