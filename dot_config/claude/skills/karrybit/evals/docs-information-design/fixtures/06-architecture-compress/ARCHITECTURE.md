# アーキテクチャ

## はじめに

このドキュメントでは、notebin のアーキテクチャについて説明します。アーキテクチャとは、ソフトウェアの全体的な構造のことであり、システムを理解するうえで非常に重要です。このドキュメントを読むことで、notebin がどのように動作しているのかを理解できるようになるでしょう。

## 全体像

notebin は、テキストスニペットを共有するための Web アプリケーションです。notebin は 1 つのバイナリで構成されており、HTTP サーバー、テンプレートレンダリング、データ永続化のすべてをそのバイナリが担当しています。つまり、notebin は単一のバイナリとしてデプロイされます。

## データベースの選定

データベースの選定は、アプリケーション設計において最も重要な判断の一つです。適切なデータベースを選ぶことで、パフォーマンス、運用性、拡張性に大きな影響があります。私たちはさまざまな選択肢を慎重に検討しました。

最終的に、私たちは SQLite を採用しました。SQLite は世界で最も広く使われているデータベースエンジンであり、信頼性が高く、多くのプロジェクトで実績があります。

SQLite を選んだ理由は、notebin が単一ノードで動作する前提であり、別プロセスのデータベースサーバーを運用するコストを避けたかったからです。想定する規模（1 日あたり書き込み数千件、読み取り数十万件）であれば、SQLite の WAL モードで十分な性能が出ることをベンチマークで確認しています（`bench/README.md` を参照）。

検討したが採用しなかった選択肢は次のとおりです。

- **PostgreSQL**: 機能面では優れていますが、notebin の利用者の多くは小規模なセルフホストであり、データベースサーバーの運用・バックアップ・バージョンアップを求めるのは導入の障壁が高すぎると判断しました。
- **BoltDB（bbolt）**: 組み込みで運用コストは低いですが、全文検索とアドホックな集計クエリが必要になったときに SQL がないと実装コストが大きいため見送りました。

## 重要な制約

SQLite を採用したことにより、notebin には重要な制約があります。**notebin のプロセスは同時に 1 つしか起動してはいけません。** 複数のインスタンスが同じデータベースファイルに書き込むと、NFS などのネットワークファイルシステム上ではロックが正しく機能せず、データベースが破損するおそれがあります。このため、Kubernetes で動かす場合も `replicas: 1` と `strategy: Recreate` を使ってください。RollingUpdate を使うと、更新中に一時的に 2 つのプロセスが同時に動いてしまいます。

## バックアップ

バックアップはとても大切です。データを失うと、取り返しがつきません。そのため、notebin ではバックアップの仕組みを用意しています。

notebin は Litestream によるレプリケーションを前提としており、WAL を S3 互換ストレージへ継続的に送ります。`cp` でデータベースファイルをコピーする方法は、書き込み中にコピーすると壊れたファイルができるため推奨しません。どうしても手動で取得する場合は `sqlite3 notebin.db ".backup backup.db"` を使ってください。

## 将来の拡張

将来、notebin がより大規模に使われるようになった場合には、アーキテクチャを見直す必要があるかもしれません。その場合は、PostgreSQL への移行を検討することになるでしょう。データアクセスは `store` パッケージのインターフェースに閉じているので、移行時に変更が必要なのは主にこのパッケージです。

## まとめ

まとめると、notebin は単一バイナリ・SQLite・Litestream という構成をとっています。この構成により、運用コストを低く抑えつつ、必要十分な性能と信頼性を実現しています。
