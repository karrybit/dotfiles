# 開発の引き継ぎの契約

- この契約は、5 つの役（要求・設計・進め方・実装・検証）と、役に仕事を渡す呼び出し側の約束。役どうしは互いの手順を知らず、この契約の項目だけで成果物をやり取りする。
- 成果物の置き場所、許可の範囲、タスクの管理は、呼び出し側が依頼に書く。

## 成果物と持ち主

| 成果物 | 持ち主 | 中身と ID |
| --- | --- | --- |
| Requirements | 要求の役 | 目的、利用者、要求 `R-n`、受け入れ条件 `AC-n`、前提 `A-n`、範囲の外、未決 `Q-n`（重要度つき） |
| Design Doc | 設計の役 | 不変条件 `INV-n`、責務の境界、契約、決定とトレードオフ、未検証の前提 `U-n` |
| Delivery Plan | 進め方の役 | 不確実性 `K-n`、インクリメント `I-n`、順序と並列、ゲート、残るリスク、計画を見直す条件 |
| 実装とテスト | 実装の役 | 変更、テスト、実行の証拠 |
| Verification Report | 検証の役 | 判定、`AC-n` と `INV-n` ごとの状態、指摘 |

- 成果物の意味を変える直しは持ち主だけが行い、ほかの役は指摘として持ち主に返す。
- 意味を変えない直し（誤字、切れたリンク）は、見つけた役が直して報告に書く。
- 付けた ID は番号を変えずに使い続け、要らなくなった項目は「取り下げ」と書いて残す。

## 引き継ぎの項目

依頼と報告は、次の項目を持つ。当てはまらない項目は「なし」と書く。

- 目的: この仕事で成り立たせること
- 関わる要求: `AC-n`・`R-n` の ID
- 設計の制約: `INV-n`・契約の ID
- 今回の範囲: `I-n` と、触ってよい場所
- 確かめる条件: 何をどう観測したら満たしたと言えるか
- 証拠: 実行したコマンドと出力の要点、ファイルと行、URL
- 決めたこと: 決めた人と出典
- 残る問題: 下の指摘の形
- 次の行動: 誰が何をするか

- 会話やログの全文の代わりに、成果物のパスと、前の引き継ぎから変わったところを渡す。

## 証拠の状態

条件ごとの状態は、次の 4 つの語で書く。

| 語 | 意味 |
| --- | --- |
| 確かめた | 呼び出し側が同じ手順で再現できる証拠がある |
| 反している | 反していることを示す証拠がある |
| 証拠不足 | 証拠はあるが判断できない（実装者の申告だけ、mock だけ、ログに呼び出しが出ただけ） |
| 確かめられない | 環境・権限・費用のために確かめを行えなかった。理由を添える |

- 仮実装（stub、mock、固定のデータ、手で置いたファイル）の上で満たした条件は、「確かめた（仮実装: <何を何で置き換えたか>）」と書き、本物での確かめを残る問題に書く。

## 指摘の種類と返す先

| 種類 | 返す先 |
| --- | --- |
| Requirement Issue（要求の欠け・矛盾・検証できない条件） | 要求の役 |
| Design Issue（責務・契約・不変条件の誤りや欠け） | 設計の役 |
| Delivery Issue（順序・ゲート・仮実装の扱いの誤り） | 進め方の役 |
| Implementation Issue（コードかテストの誤り） | 実装の役 |
| Verification Issue（検証の手順や判定の誤り） | 検証の役 |
| Environment / Permission Issue（環境・権限・費用の不足） | 呼び出し側 |

- 指摘には、種類、場所、内容、根拠、影響、確かめ方、推奨、確信度（高・中・低）を書く。
- 複数の種類にまたがる指摘は、原因のある役を 1 つ選んで返す先にし、ほかの役を「関係」に書く。
- 要求の変更、権限、不可逆な操作、費用のかかる操作は、呼び出し側の判断として「決めてほしいこと」に書いて返す。

## 報告

- 完了の報告は `karrybit:completion-report` の見出しで書き、続けて `## 引き継ぎ` の見出しに上の「引き継ぎの項目」を書く。
