# システムを調べる

- 既存のシステムを調べ、問いに証拠つきで会話で答える。製品のコード、設定、作業ツリーは変えない。
- 今の構造と動作は pstack の `how`、過去の決定と理由は pstack の `why` の手順で調べる。この skill は、どちらを使うかを決め、答えに下の「証拠の規則」を当てる。

## 手順

1. 問いを 1 行で書き、答えに要る証拠と、調べるのを止める条件を決め、下の表で調べ方を 1 つ選ぶ。
   完了条件: 問い、要る証拠、止める条件、選んだ調べ方が手元にある。
2. 選んだ調べ方で調べる。`how` と `why` は、下の「pstack の使い方」に従う。止める条件に達したら、追っていない先を書き留めて止める。
   完了条件: 問いに答える主張のそれぞれに、証拠の規則に沿った出典か「推測」「未確認」の印がある。
3. 結論を左右する主張のそれぞれについて、出典の箇所を開き直して、主張と食い違わないことを確かめてから答える。
   完了条件: 答えを返した。確かめていないことがあれば、答えの最後の `確かめていないこと` の節にある。

| 問い | 調べ方 |
| --- | --- |
| 今の動作を問い、1 つの関数、ファイル、設定の値を読めば答えが出る | 直接読む。pstack は使わない |
| 今の構造、動作、処理の経路、データの流れ、置き場所 | `how` |
| 過去の決定、その理由、トレードオフ（答えが 1 つの commit にありそうでも） | `why` |
| 今の動作と、そうなった理由の両方 | `how` のあとに `why`。2 つの結果を 1 つの答えにまとめる |

## pstack の使い方

- pstack のフォルダ `<pstack>` は、`claude plugin list --json` の出力で `id` が `pstack@` で始まる項目の `installPath` にする。
- 表で `how` か `why` を選んだら、リポジトリが小さくても、`<pstack>/skills/how/SKILL.md` か `<pstack>/skills/why/SKILL.md` を Read ツールで開いて、その手順を、指定どおりの subagent の起動も含めて最後まで行う。pstack の `how` と `why` は `disable-model-invocation` のため、Skill ツールでは呼べない。
- pstack が subagent に渡す prompt には、問いと止める条件と、下の「証拠の規則」を足す。
- Read ツールがその SKILL.md を開けなかったときだけ、直接読んで調べ、答えに pstack を使えなかったことと Read のエラーを書く。

## 証拠の規則

- 重要な主張には、`path:line`（commit `<短い hash>`）、commit の hash、文書の版、実行したコマンドとその出力のどれかを出典に付ける。
- 出典を付けられない主張は「推測」か「未確認」と書き、確かめる方法を添える。
- コード、設定、テスト、IaC、実行の結果、git の履歴、ADR を、README、コメント、wiki より先に読む。
- 文書とコードが食い違うときは、両方の箇所を挙げて食い違いと書き、今の動作はコードか実行の結果で答える。
- コードを読んでわかったことは「コード上は」、実行して見たことは「実行して確かめた」と書き分ける。
- 処理の経路は、入口から終端まで、関数の呼び出しのほかに非同期の処理、イベント、永続化、ネットワーク越しの呼び出しもたどる。
- 証拠が足りず結論を決められないときは、決められないと書き、候補の説明と、それぞれを確かめる方法を書く。
- 動かして確かめるときは、作業ツリーの外の一時のフォルダ（環境の説明にある scratchpad。なければ `mktemp -d` で作るフォルダ）に写して動かす。
- 図は、関係が文で追いにくいときだけ付ける。
