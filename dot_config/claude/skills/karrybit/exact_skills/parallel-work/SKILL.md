# worktree での並行実行と draft PR

対象: `$ARGUMENTS`。未指定なら、何を並行して進めるかをユーザーに確認する。

`karrybit:analyze-tasks` の出力があれば入力に使うが、前提にはしない。
作業の一覧がどこから来ても、この手順は成立する。

## 作業全体にかかる規則

- 1作業 = 1ブランチ = 1worktree = 1 draft PR にし、1つの worktree
  に2作業を入れない。
- PR は `gh pr create --draft` で作り、subagent に委譲するときも指示に
  `--draft` を含める。
- `gh pr ready` は実行しない。draft の解除はユーザーが明示的に求めたときだけで、
  そのときもユーザー自身に実行してもらう。
- `git push` には `-u` / `--set-upstream` を付けない。理由:
  `push.default = current` で足りる。
- タスクファイルには進行状態も PR 番号も書かず、`git worktree list` と
  `gh pr list --state all --json number,headRefName,isDraft,state`（1件なら
  `gh pr list --head <branch>`）から導出する。理由:
  ファイルに写すと変更ごとに書き換えが要り、二重の真実の源になってずれる。
- タスクファイルへの書き込みは、マージ時のチェックボックス1文字と、
  着手前の並行数の上限の1行だけにする。
- 範囲外で見つけたことは直さず、タスクファイルの「対象外・保留」へ戻す。
- draft PR の数は、人間がレビューできる数として手順 2 でユーザーと合意した
  並行数の上限以内に保ち、上限に達している間は次の波に着手しない。
  `karrybit:analyze-tasks` の出力にこの値はなく、決めるのはこの手順である。

## 手順

1. 「着手条件」に従って、受け取った各作業が着手できるかを確かめる。
   完了条件: 各作業が5つの条件をすべて満たすか、分割に戻されている。
2. 並行数の上限を具体値で決め、着手前にユーザーと合意する。
   タスクファイルがあれば、ヘッダーの `生成元` 行の直後に
   `- 並行数の上限: <値>` を追記する。
   完了条件: 合意した上限の値が会話にあり、
   タスクファイルがあればその行が書いてある。
3. 「命名」に従って、各作業のブランチ名と worktree のパスを決める。
   完了条件: すべての作業に、ID を含むブランチ名と worktree のパスがある。
4. 「worktree と subagent」に従って、作業ごとに subagent を起動する。
   完了条件: 各 subagent が、指示の骨格の手順 5 の項目をすべて報告している。
5. 「統合順序と追随」に従って、マージの順序を守り、残る作業を追随させる。
   完了条件: 直列鎖の各 PR が上流のマージ後にマージされている。
6. 「マージ後の後片付け」に従って、マージ済みの作業の worktree
   とブランチを消す。
   完了条件: `git worktree list` と `git branch` に、マージ済みの作業の
   worktree とブランチが残っていない。

## 着手条件

受け取った各作業が次をすべて満たすかを確かめる。1つでも欠けるなら着手せず、
分割してから戻る（`karrybit:analyze-tasks` をその用途に使えるが、必須ではない）。

- 目的を1文で、「かつ」を使わずに言える
- 単体でビルドとテストが通る
- 単体でレビューできる
- 単体で revert できる
- 同時に進める他の作業と同じファイルを触らない

最後の条件は念入りに確かめる。理由: 同じファイルを触る2作業を並行させると、
レビューではなくマージで問題が出る。触るなら、直列化するか、
機械的に解決できる形（表の1行追加など）に限定する。

`karrybit:analyze-tasks` を使っているリポジトリでは、タスク一覧が固定パスの
`.analyze-tasks/backlog.md` にあるので、引数で渡されなくてもここを見る。
無ければ、渡された作業だけで進める。

## 命名

タスク ID は Issue 番号（`#46`、ローカル分割した子は `#44-1`）にする。
名前に使うときは `#` を外す。Issue が無い作業は、ID の代わりに短い slug を使う。

| 対象 | 規則 | 例 |
| --- | --- | --- |
| ブランチ | `<ID>-<短い説明>` | `46-notify-deploy-status` / `44-1-aws-secrets` |
| worktree | `.claude/worktrees/<ID>` | `.claude/worktrees/46` / `.claude/worktrees/44-1` |

ブランチ名に ID を入れる。理由: `git branch` と `git worktree list` だけでどの
Issue の作業かが分かり、後片付けで消す対象を特定できる。

## worktree と subagent

- 作業ごとに subagent を `isolation: worktree` で起動する。
  `worktree.baseRef = "fresh"` なので、worktree は origin
  のデフォルトブランチ起点になる。
- 順序依存のある作業の worktree だけは、
  `git worktree add .claude/worktrees/<id> -b <branch> <親ブランチ>`
  で手動で作る。
- worktree は新規チェックアウトなので、依存をインストールする。gitignore
  された前提ファイル（`.env` など）があるリポジトリには、`.worktreeinclude`
  を置く。
- 指示の骨格の手順 1 を省かせない。理由: harness の自動命名に任せると、
  マージ後に削除すべきブランチを特定できない。

subagent に渡す指示の骨格:

```text
あなたの作業ディレクトリはこの worktree です。ここから出ないこと。

1. 最初に `git switch -c <branch>` でブランチを作る
2. 次の1件だけを実装する: <目的を1文で>
   変更してよい範囲: <ファイル / ディレクトリ>
   これ以外は直さない。作業中に別の問題を見つけたら、直さず報告に書く
3. 検証: <コマンド>
4. 最初のコミットを作ったら、その時点で push して draft PR を作る
   `git push`（`-u` は付けない）
   `gh pr create --draft --body-file <path>`
5. 報告: ブランチ名、PR 番号、検証の結果、実施できなかった検証、範囲外で見つけたこと
```

### 既知の制約

- `git worktree add` / `remove` は、`.git/config`
  への書き込みをサンドボックスに拒否されることがある。
  既知の権限ゲート操作と同じ扱いで、初回から承認を求める。
  リポジトリごとに挙動が違うので、拒否されてから試すのではなく先に確かめる。
- worktree セッションでは、静的に追跡できないシェル構文（非クォート区切りの
  heredoc `<<EOF` と brace 展開）がブロックされる。PR 本文は `--body-file`
  で渡し、複合コマンドは分けて実行する。
- メインチェックアウトへの編集と、`git -C` / `GIT_DIR` / `GIT_WORK_TREE`
  経由のリダイレクトはブロックされる。これは意図された隔離なので、回避しない。

## draft PR

draft PR は最初のコミットの直後に作る。理由: 最後にまとめて作ると、draft
が作業中であることの可視化として機能しない。

本文には次の項目をすべて入れる:

| 項目 | 理由 |
| --- | --- |
| 対象 Issue | ローカルのタスクと Issue の対応を PR 側からも辿れるようにする |
| この PR が担う作業 | 1単位であることを示す |
| 対象外 | 同じ Issue の残りをレビュアーが探さないようにする |
| 実施した検証と結果 | |
| 実施できなかった検証 | 省くと「全部通った」と読まれる |
| 依存する PR | 先にマージすべきものがあるなら明記する |

## 統合順序と追随

- 直列鎖は上流からマージする。独立な作業は任意の順でよい。
- 先にマージされた作業があっても、残る worktree は draft のまま進める。base
  の更新は後追いでよく、競合が出た時点で rebase する。

## マージ後の後片付け

環境を clean に戻すまでを1作業とする。

1. 自分が作った worktree を `git worktree remove .claude/worktrees/<id>`
   で外す。理由: worktree に出ているブランチは削除できないので、
   ブランチの削除より先に行う。
   完了条件: `git worktree list` にその worktree がない。
2. ブランチの削除は `git-vacuum` に任せ、呼び出し方と承認の手順は
   `~/.local/share/agents/docs/git-and-github.md` に従う。
   完了条件: `git branch` にマージ済みのブランチが残っていない。
3. `git worktree list` で想定外の worktree が、`git branch`
   でマージ済みのブランチが残っていないことを確かめる。
   完了条件: 両方の出力に、想定外の項目がない。
4. タスクファイルがあれば、そのタスクのチェックボックスを入れ、
   他の欄は触らない。
   完了条件: この段でのタスクファイルの差分が、そのチェックボックス1文字だけである。
