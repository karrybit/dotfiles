# 開発の引き継ぎの契約

- この契約は、5 つの役（要求・設計・進め方・実装・検証）と、役に仕事を渡す呼び出し側の約束。役どうしは互いの手順を知らず、この契約の項目だけで成果物をやり取りする。
- 成果物の置き場所、許可の範囲、タスクの管理は、呼び出し側が依頼に書く。

## 成果物と持ち主

| 成果物 | 持ち主 | 中身 |
| --- | --- | --- |
| Requirements | 要求の役 | 目的、利用者、要求、受け入れ条件、前提、範囲の外、質問（重要度つき） |
| Design Doc | 設計の役 | 部品、不変条件、責務の境界、契約、決定とトレードオフ、まだ確かめていない前提 |
| Delivery Plan | 進め方の役 | 不確実性、インクリメント、順序と並列、ゲート、残るリスク、計画を見直す条件 |
| 実装とテスト | 実装の役 | 変更、テスト、実行の証拠 |
| Verification Report | 検証の役 | 判定、`ACCR-n` と `IVCD-n` ごとの状態、指摘 |

- 成果物の意味を変える直しは持ち主だけが行い、ほかの役は指摘として持ち主に返す。
- 意味を変えない直し（誤字、切れたリンク）は、見つけた役が直して報告に書く。
- `ASMP-n` は人に確かめる要求の前提、`UCTN-n` は調査か実験で確かめる設計の技術の前提、`DLVR-UCTN-n` は計画が確かめる不確実性。
- `UCTN-n` は、外れたとき採否か `IVCD-n`・`CNTR-n` が変わる「止める」と、後続の確かめで足りる「後で」に分ける。「止める」が残る Design Doc は承認に進めず、「後で」の `UCTN-n` は `DLVR-UCTN-n` に引き継ぐ。
- 成果物の主張には、出典（ファイルと行、URL と版、人の答え）か前提（`ASMP-n`・`UCTN-n`）の印を付ける。どちらもない断定は書かない。

## ID

- 成果物の項目の ID は、下の表の prefix を使って `PREFIX-番号`（`RQST-1`）の形で書き、番号は種類ごとに 1 から振る。
- 決定の ID は、出どころの成果物や枝の字を付けない `DCSN-番号` の通し番号にする。
- 付けた ID は番号を変えずに使い続け、要らなくなった項目は「取り下げ」と書いて残す。
- 指摘の ID は、返す先の役ではなく、その指摘を書いた役の `*-POINT` で振る。設計の役が要求の役に返す指摘は `DSGN-POINT-1` になる。

| 種類 | prefix |
| --- | --- |
| 要求 | `RQST` |
| 受け入れ条件 | `ACCR` |
| 前提 | `ASMP` |
| 質問 | `QSTN` |
| 部品 | `PART` |
| 契約 | `CNTR` |
| 不変条件 | `IVCD` |
| 決定 | `DCSN` |
| 手作業 | `MNAL` |
| まだ確かめていない前提 | `UCTN` |
| Delivery Plan の不確実性 | `DLVR-UCTN` |
| インクリメント | `ICMT` |
| ゲート | `GATE` |
| 要求の役が書いた指摘 | `RQST-POINT` |
| 設計の役が書いた指摘 | `DSGN-POINT` |
| 進め方の役が書いた指摘 | `DLVR-POINT` |
| 実装の役が書いた指摘 | `IMPL-POINT` |
| 検証の役が書いた指摘 | `VRFY-POINT` |

## 引き継ぎの項目

依頼と報告は、次の項目を持つ。当てはまらない項目は「なし」と書く。

- 目的: この仕事で成り立たせること
- 関わる要求: `ACCR-n`・`RQST-n` の ID と、本文を読める場所
- 設計の制約: `IVCD-n`・`CNTR-n` の ID
- 今回の範囲: `ICMT-n` と、触ってよい場所
- 確かめる条件: 何をどう観測したら満たしたと言えるか
- 証拠: 実行したコマンドと出力の要点、実行した commit の hash と環境（OS、言語の版、接続先）、ファイルと行、URL
- 決めたこと: 決めた人と出典。直したときは、変えた ID と、それに依存して見直す成果物の ID（分かる範囲）
- 残る問題: 下の指摘の形
- 次の行動: 誰が何をするか

- 会話やログの全文の代わりに、成果物のパスと、前の引き継ぎから変わったところを渡す。
- 次の役に渡してよいのは、残る問題に「完了を妨げる」もの（人に尋ねる重要度「高」の `QSTN-n`、止める `UCTN-n`、役の定義の「確定にしない条件」「計画を完了にしない条件」「状態を『確かめた』にしない条件」に当たるもの）がないとき。
- 「設計に委譲」と書いた `QSTN-n` は設計の役が調べ、答えを Design Doc に出典つきで書く。
- 影響を受けた成果物は、その持ち主が見直す。
- 止める `UCTN-n` を確かめる実験のうち設計の役が自分で行えないもの（製品の作業ツリー、共有の状態の変更、費用か権限が要るもの）は、呼び出し側が、捨てる worktree で実装の役に頼み、成果を取り込まない。
- 止める `UCTN-n` を確かめる実験を頼むときは、「目的」に答える問いを、「確かめる条件」に結果ごとの設計の分かれ目を、「今回の範囲」に隔離の場所と許可の範囲と捨てる前提を書く。
- 実験の結果は「証拠」と「決めたこと」で返し、`UCTN-n` は持ち主の設計の役が更新する。

## 証拠の状態

条件ごとの状態は、次の 4 つの語で書く。

| 語 | 意味 |
| --- | --- |
| 確かめた | 呼び出し側が同じ手順で再現できる証拠がある |
| 反している | 反していることを示す証拠がある |
| 証拠不足 | 証拠はあるが判断できない（実装者の申告だけ、mock だけ、ログに呼び出しが出ただけ） |
| 確かめられない | 環境・権限・費用のために確かめを行えなかった。理由を添える |

- 仮実装（stub、mock、固定のデータ、手で置いたファイル、ローカルの代替の環境: 別の DB、emulator、別の版、本番と違う設定）の上で満たした条件は、「確かめた（仮実装: <何を何で置き換えたか>）」と書き、本物での確かめを残る問題に書く。
- 人の承認や受け入れは状態の語に混ぜず、「決めたこと」に書く。
- Verification Report の判定は、上から順に当てて決める: `反している` か、Environment / Permission Issue のほかに完了を妨げる指摘がある→FAIL、`確かめられない` がある→BLOCKED、`証拠不足` か確かめていない範囲の項目がある→NOT VERIFIED、すべて `確かめた`→PASS。

## 指摘の種類と返す先

| 種類 | 返す先 |
| --- | --- |
| Requirement Issue（要求の欠け・矛盾・検証できない条件） | 要求の役 |
| Design Issue（責務・契約・不変条件の誤りや欠け） | 設計の役 |
| Delivery Issue（順序・ゲート・仮実装の扱いの誤り） | 進め方の役 |
| Implementation Issue（コードかテストの誤り） | 実装の役 |
| Verification Issue（検証の手順や判定の誤り） | 検証の役 |
| Environment / Permission Issue（環境・権限・費用の不足） | 呼び出し側 |

- 指摘には、ID（書いた役の `*-POINT-n`）、種類、場所、内容、根拠、影響、確かめ方、推奨、重要度（完了を妨げる・改善）、確信度（高・中・低）を書く。
- 複数の種類にまたがる指摘は、原因のある役を 1 つ選んで返す先にし、ほかの役を「関係」に書く。
- 要求の変更、権限、不可逆な操作、費用のかかる操作は、呼び出し側の判断として「決めてほしいこと」に書いて返す。

## 報告

- 完了の報告は `karrybit:completion-report` の見出しで書き、続けて `## 引き継ぎ` の見出しに上の「引き継ぎの項目」を書く。
- `## 引き継ぎ` では、依頼から変わらない項目を、依頼で「なし」なら「なし」、それ以外なら「依頼のとおり」と書く。
