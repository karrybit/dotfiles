# CLI の AI フレンドリーさをレビューする

- 対象の CLI を、下の「判定の基準」の原則ごとに判定し、根拠と改善点を返す。
- 対象の CLI で状態を変えず、CLI のソースも変えない。
- 判定の基準の出典と、指針どうしが食い違う点の決め方は、同じフォルダの `sources.md` にある。基準を直すときに読む。

## 調べるときの決まり

- 実行するのは、`--help`・`-h`・`help <サブコマンド>`・`--version` と、help が読むだけと示すサブコマンド（`list`・`get`・`view`・`status` など）だけにする。
- 作成・更新・削除・送信・ログイン・ログアウト・設定の書き込みをするサブコマンドは、`--dry-run` を付けても実行せず、help とソースで調べる。`--dry-run` を知らない CLI は、そのフラグを無視して状態を変えることがあるため。
- 読むだけかどうかを help から決められないサブコマンドは実行せず、根拠に「実行していない」と書く。
- 実行は、stdin を `/dev/null` につなぎ、stdout と stderr を別のファイルに分け、終了コードを残す形にする。`$d` は、環境の説明にある scratchpad の下のフォルダか、なければ `mktemp -d` で作るフォルダにする。

  ```sh
  <コマンド> <引数> </dev/null >"$d/out" 2>"$d/err"; echo "exit=$?"
  ```

- コマンドと引数は変数に入れず、そのまま書く。zsh は変数の中の空白で引数を分けず、`gh "pr list"` のような 1 つの引数として渡すため。

- エラーは、読むだけのコマンドに、存在しないサブコマンド・存在しないフラグ・存在しない資源の名前を渡して起こす。
- ソースのフォルダを渡されたときは、help で決められない点（終了コードの割り当て、秘密の読み方、タイムアウト）をソースで確かめ、`path:line` を根拠にする。
- help にもソースにも書いていない振る舞いは、エージェントが頼れない振る舞いとして判定し、根拠に「help に書いていない」と書く。

## 手順

1. 対象の CLI の `--version` と最上位の `--help` を読み、サブコマンドの一覧から、試す読むだけのサブコマンドを 2〜3 個と、状態を変えるサブコマンドを選ぶ。
   完了条件: 版、サブコマンドの一覧、試すコマンドの一覧、実行しないサブコマンドの一覧が手元にある。
2. 下の「判定の基準」の原則のすべてについて、「確かめ方」の呼び出しとソースの読みをする。
   完了条件: 原則のすべてに、試したコマンドとその出力か `path:line` が 1 つ以上ある。当てはまらない原則には、そう決めた根拠がある。
3. 原則ごとに判定を付け、改善点に重さを付け、下の「出力の形」で返す。
   完了条件: 出力の形の節のすべてがあり、直す順の一覧が重さの順に並んでいる。

## 判定の語と重さ

| 判定 | 意味 |
| --- | --- |
| 満たす | 原則の基準のすべてを満たす |
| 一部 | 基準の一部を満たす。満たさない基準を根拠に書く |
| 満たさない | 基準のどれも満たさない |
| 当てはまらない | 原則の前提が CLI にない。理由を書き、改善点を出さない |

| 重さ | 改善しないときに起きること |
| --- | --- |
| 高 | エージェントが止まる（入力やページャを待つ）、誤った操作をする、秘密が漏れる |
| 中 | エージェントの試行が増える（help を何度も読む、エラーの文面から次の手を推し量る） |
| 低 | 扱いやすさが上がるが、なくても使える |

- 原則の基準のうち前提が CLI にないもの（秘密を扱わない CLI の秘密の基準など）は、外して残りで判定し、外したことを根拠に書く。

## 判定の基準

### 1. 構造化出力

- 主な出力を JSON で出すオプションがあり、help に書いてある。名前は `--json` にするか、ほかの名前ならサブコマンドの間で揃える。
- stdout にはデータだけを出し、進捗・警告・エラーは stderr に出す。
- stdout が端末でないとき、色の制御文字を出さない。
- 出力の欄を足すだけにし、欄の名前を変えたり消したりしないという互換の方針が、help か文書に書いてある。
- 確かめ方: 読むだけのコマンドを JSON のオプション付きで実行し、`jq . "$d/out"` が通るか、stdout に進捗や警告が混ざらないか、制御文字（`\x1b[`）がないかを見る。help と文書で互換の方針を探す。

### 2. 意味のある終了コード

- 成功のときだけ 0 を返し、失敗のすべてで 0 以外を返す。
- 次の手が変わる失敗（使い方の誤り、対象がない、認証と権限、一時的な失敗）を、終了コードで見分けられる。
- 終了コードの割り当てが help か文書に書いてある。
- 126・127 と 128 より大きい値を、自分の意味に使わない。shell が、コマンドが見つからない・実行できない・シグナルで終わったことに使うため。
- 検索のコマンドが「見つからない」に 1 を返すなら（`grep` の慣習）、そう文書に書いてある。
- 値の決め方は問わない。`sysexits.h` の 64〜78 でも、gh の 1・2・4 のような小さな値でもよい。
- 確かめ方: 読むだけのコマンドで、存在しないサブコマンド、存在しないフラグ、存在しない資源の取得を起こし、終了コードを比べる。help と文書で `exit` を探す。

### 3. 非対話と秘密の扱い

- どのサブコマンドも、初期設定（ログインなど）を含めて、入力をフラグか引数か stdin で渡せ、対話の入力を要らない。
- stdin が端末でないとき、確認や入力を求めて止まらず、要るフラグの名前を言って失敗する。
- 確認を飛ばすフラグ（`--force`・`--confirm=<名前>` など）か `--no-input` がある。
- stdout が端末でないとき、ページャを開かない。
- 秘密を、stdin かファイル（gh の `--with-token`、`--password-file` など）で渡せる。フラグの値でしか渡せないなら満たさない側に、環境変数でしか渡せないなら一部の側に数える。
- 確かめ方: 読むだけのコマンドを stdin を `/dev/null` にして実行し、止まらずに終わるかを見る。ログインと認証のサブコマンドは実行せず、help で入力と秘密の渡し方を見る。

### 4. 名詞と動詞で揃ったコマンドの体系

- サブコマンドを持つ CLI は、名詞と動詞の 2 段（`docker container create`）で並べ、2 段の順を CLI の全体で揃え、どの名詞にも同じ操作には同じ動詞を使う。`名詞 動詞` と `動詞 名詞` のどちらの順でも、揃っていれば満たす側に数える。
- 同じ意味のフラグにサブコマンドの間で同じ名前を使い、広く使われる名前（`--json`・`--dry-run`・`--force`・`--quiet`・`--output`・`--help`・`--version`）に揃える。
- 紛らわしい似た名前のサブコマンド（`update` と `upgrade`）、任意の前方一致での省略、サブコマンドを省くと別のサブコマンドとして解釈する入口がない。
- フラグのすべてに長い形があり、`--` でオプションの終わりを示せる。
- サブコマンドを持たない CLI では、1 つめの基準を外す。
- 確かめ方: 最上位と 2〜3 個の名詞の help を読み、動詞とフラグの名前を並べて比べる。サブコマンドの名前の前の部分（`list` に対する `li` など）に `--help` を付けて渡し、出たものがそのサブコマンドの help（前方一致で動く）か、親の help かエラー（前方一致で動かない）かを見る。

### 5. help と出力の欄の自己記述

- どのサブコマンドも、`--help` で使い方・フラグ・例を stdout に出して、0 で終わる。
- JSON の出力で選べる欄の名前を、CLI から一覧で得られる（gh の、値を付けない `--json` など）。
- この skill が置く基準: 引数とフラグの型・必須か・既定の値を、機械が読める形で返す入口（`describe <サブコマンド>` の JSON、JSON Schema など）がある。エージェントの試行と取り違えを減らすため。
- `--help` だけなら一部にする。
- 確かめ方: `<コマンド> <サブコマンド> --help` を実行の形で走らせ、stdout と終了コードを見る。値を付けない JSON のオプション、`describe`、`schema` を、読むだけのコマンドで試し、help でも探す。

### 6. 行動できるエラー

- エラーが、何が誤りか（足りない引数の名前、受け付ける値）と、次に打つコマンドかフラグを言う。
- 打ち間違いには候補を示し、推した候補を確かめずに実行しない。
- 状態を変えたとき、何が変わったかを伝え、頼んだ結果と違うとき（一部だけ変わったときなど）はそう言うと、help・文書・ソースが示す。
- この skill が置く基準: 機械が読める形の出力（`--json` など）を頼んだとき、エラーも JSON で返し、次の手（次に打つコマンド、選べる値の候補、足りない引数）を欄で持つ。エージェントの試行と取り違えを減らすため。
- 確かめ方: 原則 2 で起こしたエラーの stderr を読む。同じエラーを JSON のオプション付きでも起こし、stdout と stderr を見る。状態を変えたときの出力は、help・文書・ソースで調べる。

### 7. やり直せることと `--dry-run`

- 状態を変えるサブコマンドに `--dry-run`（`-n`）があり、実行したら何が起きるかを出す。
- 途中で失敗した呼び出しを同じコマンドでもう一度実行すると、続きから進む（やり直しても結果が重ならない）と、help・文書・ソースが示す。
- 状態を変えるサブコマンドがない CLI では、当てはまらない。
- 確かめ方: help と文書とソースだけで調べ、状態を変えるサブコマンドは実行しない。

### 8. 合成しやすさ

- 1 行に 1 件を出す平らなテキスト（`--plain` など）か JSON で、`jq`・`awk`・`grep` につなげられる。
- ファイルを受け取る引数が、`-` で stdin を受け付ける。
- 付け足しの出力を消す `-q`・`--quiet` がある。
- 確かめ方: 読むだけのコマンドの既定の出力を stdout をファイルにして見て、1 行に 1 件か、表の罫線や折り返しがないかを見る。help で `-` と `--quiet` を探す。

### 9. タイムアウトと中断

- ネットワークか長い処理を使う CLI に、既定のタイムアウトがあり、フラグか設定で変えられる。
- 中断（Ctrl-C）ですぐに終わると、文書かソースが示す。
- ネットワークも長い処理も使わない CLI では、当てはまらない。
- 確かめ方: help・文書・ソースで `timeout` と `SIGINT` を探す。

### 10. 使い方の文書

- 端末で読める文書（`help <トピック>`、man のページなど）があり、入れた版の CLI と同じ内容を返す。
- 最上位の help か各サブコマンドの help に、web の文書へのリンクがある。
- この skill が置く基準: エージェント向けの手順（最初に打つコマンドの順など）を CLI と一緒に配り、その手順が手元の版のコマンドとフラグに合っている。エージェントの試行と取り違えを減らすため。
- 確かめ方: 最上位の help で、文書のトピックと web の文書のリンクを探す。CLI のリポジトリ・配布物・help のリンクで、エージェント向けの手順を探す。端末の文書とエージェント向けの手順に書いてあるコマンドとフラグを、手元の版の help と比べる。
