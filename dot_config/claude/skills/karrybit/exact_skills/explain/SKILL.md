# HTML の解説を作らせる

- HTML の解説は、1 ファイルの HTML で資料や仕組みを解説するもので、元になる説明の文書を持つ。
- この skill は、`karrybit:organize` と `karrybit:visualize` を組み合わせるオーケストレータで、2 つをつなぐ知識（続けて作らせる依頼、一緒に使う評価、型を直すとき）を持つ。説明の文書の作り方は `karrybit:organize` に、HTML の作り方は `karrybit:visualize` にある。
- 2 つの型は、[brief.md](brief.md) の型で 1 つのサブエージェントに続けて行わせる。分けると費用が増え、説明の文書で省いたことが図に移る。organize の型で作った説明の文書は、visualize の入力の「説明の文書」の形を満たすものとして、そのまま HTML 化の依頼に渡す。
- 2 つの skill のファイルは `${CLAUDE_SKILL_DIR}/../organize/` と `${CLAUDE_SKILL_DIR}/../visualize/` にある（下では `<organize>` と `<visualize>` と書く）。

## 手順

1. 材料を集める。材料は、`<organize>/SKILL.md` と `<visualize>/SKILL.md` の手順 1 の材料（元の資料の場所と版と読み方、読み手と使い道、頼まれた内容の原文、scratchpad のパス）と、HTML の書き先と、説明の文書の書き先と、控えのファイルの指定。
   - HTML の書き先が依頼にないときは、作り始めずに依頼した側に尋ねる。
   - 説明の文書の書き先は、依頼が説明の文書を残す場所を渡したときはその場所にし、フロントマターは依頼にある規則と検査のコマンドにする。依頼が残す場所を渡さないときは、scratchpad の `organize/<元の資料の名前>.md` にし、フロントマターは「なし」にする。
   - 控えのファイルは、HTML と一緒に書かせて HTML の場所と元の資料を記録するファイルで、依頼がパスと書き方の規則と検査のコマンドを渡したときだけ書かせる。渡されなければ [brief.md](brief.md) の型の 3 と控えのファイルの語を省く。
   - 元の資料が organize の型で作った説明の文書のときは、情報整理の依頼を「なし（1 を飛ばす）」にし、HTML 化の型の説明の文書をそのパスの「読むだけ」にする。

   完了条件: [brief.md](brief.md) の型と、`<organize>/brief.md` と `<visualize>/brief.md` の型の `<…>` のすべてに入れる値が手元にある。
2. `<organize>/brief.md` と `<visualize>/brief.md` の型を埋めたものを [brief.md](brief.md) の型に入れて、新しいサブエージェントに Agent tool で 1 つの依頼として頼む。
   - 2 つの型の書き出すパスは、絶対パスで依頼に書く。HTML 化の型の説明の文書は情報整理の型の書き先と同じパスにし、「直してよい」にする。HTML 化の型の置き場所は HTML の書き先にする。
   - 2 つの型の「頼まれた内容」には、頼まれた内容の原文を入れる。`<rubric.md の絶対パス>` は、情報整理の型では `<organize>/rubric.md`、HTML 化の型では `<visualize>/rubric.md` にする。

   完了条件: 依頼に、説明の文書と HTML の絶対パス（情報整理を飛ばしたときは読むだけの説明の文書と HTML の絶対パス）と、頼んだときは控えのファイルの絶対パスが書いてあり、サブエージェントの報告に、それらのパスと、2 つの依頼の「報告」の項目（HTML 化の依頼では、HTML の制作の plugin を呼んだこと）がすべてある。
3. HTML と説明の文書の絶対パス（控えのファイルを頼んだときはそれも）と、サブエージェントが報告した説明の文書の誤りと欠けを、依頼した側に返す。
   完了条件: 返事に、渡された書き先と同じ HTML の絶対パスがある。

## HTML の解説を評価するとき

- 1 つの評価役に、HTML の解説を 1 つと、`<organize>/rubric.md` と `<visualize>/rubric.md` を一緒に渡し、作るサブエージェントには渡さない。意味の観点は organize の rubric の観点 1〜6 とゲート G1〜G4、見せ方の観点は visualize の rubric の観点 1・2 とゲート G1・G2・S1〜S6 で、ゲートは rubric の名前を付けて報告させる（G1 と G2 が 2 つの rubric にあるため）。
- 評価の手順は organize の rubric の「評価のしかた」1〜6 にする。その 3 では HTML をブラウザで描画して、visualize の rubric の「評価のしかた」1 の描画の確かめも行い、その 4 の主張には、visualize の rubric のゲート G1 の大事な図のすべての線とラベルを足す。観点ごとの点の付け方の注記は、それぞれの rubric に従う。
- 描画の確かめには、`<visualize>/brief.md` の型の「制約」の chrome-devtools-mcp を使わせる。
- 評価のレポートは最後のメッセージの本文で返させ、ファイルに書かせない。

## 依頼の型を直すとき

- 対象は、この skill の [brief.md](brief.md)、`<organize>` と `<visualize>` の `brief.md` と `rubric.md`。決まりごとの出典は 2 つの `sources.md` で読み、依頼に入れない。
- 直す欠陥か仮説を決め、元の資料・生成物・生成役のログから原因の手順（どの型か rubric のどこか）を切り分けてから、その手順の指示を置き換えで最小限に直す。
- 確かめの手順（情報整理の型の手順 6、HTML 化の型の手順 3）の確かめ方か適用の条件だけを直したときは、既存の生成物にその確かめだけをさせて、欠陥を見つけるかで確かめる。これは確かめ方の効き目を示すだけで、新しい生成物が良くなったことは示さない。
- 作る手順（情報整理の型の手順 1〜5、HTML 化の型の手順 1〜2、この skill の型）を直したときは、直した手順とその下流を作り直す（直した手順の出力と下流の作業メモを固定して比べない）。性質の違う題材（元の資料と版）2 つと、直すのに使っていない題材 1 つを選ぶ（この skill で前に作った解説があれば、その元の資料から選ぶ）。題材ごとに、新しいサブエージェントに手順 2 の依頼で作らせ、別の新しいサブエージェントに「HTML の解説を評価するとき」のとおり評価させて、前の版と並べる。比べるときは、図の見た目の違いでなく、伝える事実と関係の違い（欠け・誤り）を数える。
- 作り手のモデルが替わったときは、局所の確かめで済ませず、同じ 3 つの題材を新しいモデルで情報整理から（情報整理の依頼を飛ばさずに）作り直して、前の版と並べて評価させる。
