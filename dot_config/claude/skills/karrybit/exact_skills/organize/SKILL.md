# 説明の文書を作らせる

- 説明の文書は、元の資料と版・読み手・使い道から、中心の概念・関係・動きと、問いごとの答えを根拠つきで書いた Markdown 1 ファイル。媒体と見た目は決めず、作り方の内部の段（事実・概念・筋・構成）は作り手の作業メモに置く。
- 依頼の型は [brief.md](brief.md)。型を直すときは下の「依頼の型を直すとき」に従い、決まりごとの出典は [sources.md](sources.md) にある。
- 説明の意味（正確さ・概念・関係・問いへの答え・見出しの構造）の評価の基準は [rubric.md](rubric.md)。評価するサブエージェントだけに渡し、作るサブエージェントには渡さない。

## 手順

1. 材料を集める。材料は、元の資料の場所と版（git は commit の完全な hash）と読み方、読み手と読んだあとの使い道、頼まれた内容の原文、scratchpad のパス、書き先、フロントマターの指定。読み手と使い道が依頼にないときは、元の資料を使って作業する人と、その作業にする。
   - 書き先は、依頼に指定がなければ scratchpad の `organize/<話題>.md` にする。
   - フロントマターは、依頼に規則と検査のコマンドがあるときだけ書かせ、なければ「なし」にする。

   完了条件: 型の `<…>` のすべてに入れる値が手元にある。
2. [brief.md](brief.md) の型の `<…>` を埋めて、新しいサブエージェントに Agent tool で頼む。型の `<rubric.md の絶対パス>` は `${CLAUDE_SKILL_DIR}/rubric.md` にする。
   完了条件: サブエージェントの報告に、説明の文書と model.md のパスと、確かめた主張の数がある。
3. 説明の文書の絶対パスと、確かめた主張の数を、依頼した側に返す。
   完了条件: 返事に説明の文書の絶対パスがある。

## 依頼の型を直すとき

- 対象は [brief.md](brief.md) と [rubric.md](rubric.md)。決まりごとの出典は [sources.md](sources.md) で読む。sources.md は依頼に入れない。
- 直す欠陥か仮説を決め、元の資料・生成物・生成役のログから原因の手順（型か rubric のどこか）を切り分けてから、その手順の指示を置き換えで最小限に直す。
- 確かめの手順（型の手順 6）の確かめ方か適用の条件だけを直したときは、既存の生成物にその確かめだけをさせて、欠陥を見つけるかで確かめる。これは確かめ方の効き目を示すだけで、新しい生成物が良くなったことは示さない。
- 作る手順（型の手順 1〜5）を直したときは、直した手順とその下流を作り直す（直した手順の出力と下流の作業メモを固定して比べない）。前に作った説明の文書のうち性質の違う題材（元の資料と版）2 つと、直すのに使っていない題材 1 つで、新しいサブエージェントに型で作らせ、別の新しいサブエージェントに [rubric.md](rubric.md) で評価させて、前の版と並べる。比べるときは、伝える事実と関係の違い（欠け・誤り）を数える。
- 評価させるサブエージェントには、評価のレポートを最後のメッセージの本文で返させ、ファイルに書かせない。
- 作り手のモデルが替わったときは、局所の確かめで済ませず、作る手順を直したときと同じ 3 つの題材を新しいモデルで手順 1 から作り直して、前の版と並べて評価させる。
