# 情報整理の依頼の型

`SKILL.md` の 2 で、下の型の `<…>` を埋めて依頼にする。

- 型の外の文（作り方の好み、前の版の感想）は依頼に足さない。足すと、作り手が型より依頼の言葉に合わせる。

<template>
# <元の資料の名前> の説明の文書を作る

## 目的
<読み手> が、<元の資料の名前> の中心の概念と、概念どうしの関係と、動き（流れ・状態の移り変わり）を掴み、必要なところだけ仕様の詳細まで確かめられる説明の文書を、根拠つきで作る。読み手は <何を知っていて、読んだあと何に使うか>。頼まれた内容: <依頼の原文>

## 入力
- 元の資料: <場所と版と読み方（git はリポジトリのパスと commit の完全な hash で、`git show <commit>:<path>` と `git ls-tree` で読む。Confluence などはページの id と版と、読む道具と版の確かめ方）>。元の資料とそれが参照するファイルを読み、checkout・fetch・書き込みをしない。
- 書き先: `<説明の文書の絶対パス>`（Markdown の 1 ファイル）
- フロントマター: <依頼にフロントマターの規則があるときは「<規則と、入れる値>に従う。検査のコマンドは <コマンド>」、それ以外は「なし」>
- 作業メモ: <scratchpad のパス>/model.md（説明の文書には写さない）

## 手順
1. 元の資料と、それが参照するコード・設定・文書を、章立てでなく対象の仕組みを知るために読む。
   完了条件: model.md の「事実」に、定義・仕様・制約・保証・例外・振る舞い・未決が、元の資料のパスと行つきである。資料どうしと、資料と実物（コード・設定）の食い違いと、確かめられなかったことに印がある。資料に書いていない推論には「推論」の印がある。
2. 対象の概念モデルを model.md の「概念」に書く。
   - 中心の概念と周辺の概念を分け、概念ごとに、定義の 1 文、責務、境界（何を受け持たないか）を書く。
   - 同じものの別名と、似ているが違う概念を、区別とともに書く。
   - 関係は「A —動詞→ B」の形で、向きと意味（構成・包含・依存・呼び出し・因果・順序・遷移・対比など、対象に合う種類）と出典を書く。「関連する」「つながる」で済ませない。
   - 動き（流れ、状態の移り変わり、やりとり）と、それを縛る制約と例外を書く。

   完了条件: 中心の概念だけを使って、対象が何をするかを 3 文以内で説明した段落が model.md にあり、どの関係にも動詞と向きと出典か「推論」の印がある。
3. 説明の筋を model.md の「筋」に書く。読み手の大事な問いを、読み手の理解の順（全体像から詳細へ、静的な構造から動きへ、基本から例外へ）に並べ、問いごとに、答えの 1 文、要る概念と関係、要る詳細の深さ、根拠の事実を書く。読み手の問いに効かない事実は、載せないか、詳細を確かめるための参照の節に回すと決める。
   完了条件: 中心の概念のどれもが、いずれかの問いの答えで説明される。1 の食い違いと未確認のどれもが、載せる場所か載せない理由を持つ。
4. 見出しの構成を、見出しだけのアウトライン（`##` と `###`）で model.md の「構成」に書く。概念と筋は見出しに写さず、読み手が全体の地図を掴んでから関心のある部分へ降りられる形に組み直す。
   - 最初の `##` は全体像の節にし、2 の 3 文の説明、中心の概念の定義、全体の関係と、対象の動きのうち複数の部分をまたぐもの（1 件が部品を通って消えるまで、など）の答えを置き、部分の節からここを参照する。
   - 全体像の節に続く `##` は、3 文の説明に出る対象の主な部分ごとに 1 つ置き、並べるだけで対象の全体の構成を言えるようにする。
   - 同じ親の直下は、対象の概念の構造と読み手の使い道に合う 1 つの分類の軸（構成要素、処理の段階、ライフサイクル、主体の責務など）で分け、抽象度を揃える。別の軸で分けたいものは別の親の下に置く。選んだ軸と、選ばなかった軸とその理由を書く。
   - アウトラインは `###` までにする。節の中で小見出しが要るときは `####` を使ってよい。
   - 3 の問いは見出しに 1 つずつ並べず、問いごとに答えを置く節を 1 つ決める。
   - 節を、理解のための説明の節、作業の節、確かめるための参照の節（値・パラメータ・フィールドの一覧、食い違いと確かめられなかったこと）に分け、説明・作業・参照の順に置く。作業の節は、読み手の使い道が作業（足す・設定する・失敗や拒否の原因を切り分ける など）のときだけ作り、作業ごとに部分をまたいで手順と判断をまとめ、説明の節を参照する。
   - 見出しは元の資料の章立てでなく、選んだ軸から作る。見出しの言葉は、その節の本文の条件と同じ向きに読める語にする（止まった Agent を扱う節に「動いている Agent に」と付けない）。

   完了条件: アウトラインだけを読み直して次のすべてが成り立ち、成り立たないところは書く前に構成から直してある。最上位の見出しだけで対象の全体の構成を言える。全体像・作業・参照の節を除く同じ親の直下の見出しのどれもが、選んだ軸の同じ問い（「どの部品か」「どの段階か」など）への答えになり、抽象度が揃う。どの `###` も、親の `##` の名前が指すものの一部か一種になる。中心の概念のどれもが、どこかの見出しの下に入る。並びが全体像から詳細へ、説明から作業と参照へ進む。同じ話題（失敗したときの挙動など）を説明・作業・参照の 2 か所以上に書かず、1 か所に書いてほかから参照する。3 の問いのそれぞれについて、アウトラインだけで予想した節が、答えを置くと決めた節と合う（model.md に問いごとの 2 つの節の表がある）。
5. 説明の文書を書き先に書く。model.md の段の名前や中間の一覧は写さず、そのまま読める文書にする。
   - 入力のフロントマターが「なし」でないときは、1 行目からフロントマターを書き、続く空行のあとに本文を書く。
   - `#` の題の直後に、元の資料の場所と版と読み方、読み手と使い道、頼まれた内容を箇条で書く。
   - `##` と `###` は 4 のアウトラインのとおりにする。
   - 全体像の節に、2 の 3 文の段落、中心の概念ごとの定義の 1 文・責務・境界、似た名前の区別、全体の関係の一覧、部分をまたぐ動きを置く。全体像の節の最後に、見出しを付けずに「この文書が答える問い:」で始まる箇条を置き（見出しにすると、アウトラインの中で対象の部分と同じ階層に文書の案内が並ぶため）、3 の大事な問い（3〜7 個）ごとに、答えの節へのリンク（`[節の名前](#アンカー)`）を書く。
   - 関係の一覧は「A —動詞→ B（関係の種類。出典）」の箇条にし、どの関係も文書の中で 1 回だけ書く。部分の節では、その節の本文で関係を説明し、一覧の箇条を繰り返さない。
   - 動き（流れ・状態の移り変わり・やりとり）は番号つきの並びで書き、分岐と戻りと、失敗と例外が止まる位置を書く。同じ動きを全体像と部分の節の両方で書くときは、同じ分岐と戻りを持たせる。
   - どの `##` と `###` の節も、見出しの直後に、その節が答える問いの答えの 1 文を置き、その下に根拠と詳細を書く。
   - 主張ごとに元の資料の位置（パスと行、ページの節の名前）を書く。推論・未確認・未決・食い違いは語の印で示す。食い違いと確かめられなかったことは参照の節の 1 つの `###` に集め、本文から参照する。

   完了条件: 書き先に文書があり、`##` と `###` が 4 のアウトラインと同じで、題の直後に元の資料と読み手の箇条があり、全体像の節に 3 文の段落と概念の定義と関係の一覧と「この文書が答える問い」がある。
6. 説明の文書の主張を確かめて直す。冒頭の段落、各節の答えの文、関係の一覧、動きの並びについて、主張ごとに元の資料の行を開いて確かめる。「〜がない」「決まっていない」と書く主張は、範囲（あるファイル、ある skill、関わる skill の群、仕組み全体）を主張の中に書き、その範囲の資料を読んで確かめる。検索で当たらなかったことだけを根拠にせず、読みきれない範囲は主張から外すか「未確認」にする。全体像の動きと部分の節の動きを並べ、分岐と戻りを突き合わせる。見出しごとに、直後の 1 文がその節の答えになっているかを数える。合わないところは、文書だけでなく、原因のある model.md の概念・筋・構成から直す。
   完了条件: 確かめた主張の数と、直した箇所の一覧が報告にある。フロントマターを書いたときは、入力のフロントマターの検査のコマンドが問題を 0 件出した。元の資料と食い違う主張が 0 で、「ない」と書いた主張のどれもに範囲と読んだ資料があり、全体像と部分の節で分岐か戻りの違う動きが 0 で、本文の条件と逆に読める見出しが 0 で、見出しの直後に答えの 1 文がない `##` と `###` の節が 0。

## 制約
- 書いてよいのは、書き先と作業メモの場所だけ。
- git の commit はしない。秘密の値（トークン、鍵、アカウント番号など）と個人情報（人の名前など）を入れない。
- コマンドは sandbox の中で動かし、sandbox の外で動かさない。
- `<rubric.md の絶対パス>` は読まない（型を直すときの評価に使うため）。
- 手段を simple & easy にし、既存のツールやライブラリで済むなら作らない。

## 報告
- 説明の文書と model.md のパス。
- 最上位の見出しと、選んだ分類の軸とその理由。
- 中心の概念。
- 確かめた主張の数と、直した箇所。
- 資料と実物の食い違いと、確かめられなかったこと。
- 新しく作ったものと、探した既存のツール、それを使わなかった理由（なければ「なし」）。
- 考えた中でいちばん simple & easy な案より複雑にしたところと、それを求める本質的な複雑さ（なければ「なし」）。
- 検討したうえで扱わないことにしたコーナーケースと、扱わない理由（なければ「なし」）。
</template>
