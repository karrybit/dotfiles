# HTML 化の依頼の型

`SKILL.md` の 2 で、下の型の `<…>` を埋めて依頼にする。

- 型の外の文（作り方の好み、前の版の感想）は依頼に足さない。足すと、作り手が型より依頼の言葉に合わせる。

<template>
# <元の資料の名前> の説明の文書を、1 ファイルの HTML にする

## 目的
説明の文書の意味（中心の概念、関係、動き、問いごとの答え、確かさの印、出典）を変えずに、読み手が HTML で全体を掴み、必要なところだけ仕様の詳細まで確かめられるようにする。読み手と使い道と頼まれた内容は、説明の文書の題の直後の箇条にある。

## 入力
- 説明の文書: `<説明の文書の Markdown の絶対パス>`。<「直してよい」か「読むだけ」>。中心の概念と関係と動きと「この文書が答える問い」は全体像の節に、見出しのアウトラインは `##` と `###` に、元の資料の場所と版と読み方は題の直後にある。事実の洗い出しと構成はやり直さない。
- 元の資料: 説明の文書の題の直後にあるもの。説明の文書と HTML の主張を確かめるときと、説明の文書の誤りや欠けを見つけたときだけ開き、checkout・fetch・書き込みをしない。
- 置き場所: `<index.html の絶対パス>`
- 作業メモ: <scratchpad のパス>/presentation.md

## 手順
1. 問いごとの見せ方を presentation.md の「見せ方」に書く。答えに関係が出る問いは、表や文にする前に、答えを概念と関係（もの・主体と、その間の動詞・順序・境界・対比）にまとめて図にする案を作る。図の形は、答えに出る関係の意味（説明の文書の関係の種類）を、同じ意味を読み手が受け取る見た目に写して選ぶ: 包含と所有は内側に置く囲み、階層は入れ子か木、順序と時間は 1 本の軸の上の位置、対比と対立は同じ記法で横に並べるか軸の両端に置く、共通部分は重なり、主体と対象の組ごとに決まる関係（権限など）は行列、依存・呼び出し・因果・遷移は向きのある線、やりとりとその境界はシーケンス図。重なりは共有する要素があるときだけ、大きさと帯の幅は資料に量があるときだけ使い、ページのどの図でも、同じ意味には同じ見た目（色・線・印）を使い、意味の違う関係と印に同じ見た目を使わない。候補の図法と描き方は `plannotator-effective-html:html` の参照（`references/diagrams.md`、量があれば `references/charts-and-data.md`）に従う。資料どうしの食い違いは 2 つの形を同じ記法で並べた図に、失敗と例外は正常の流れの図の上に止まる位置を印で載せた図にする案を作る。図の案が決定表・表・文より遅く分かるとき（条件の組み合わせ、値の一覧、単純な繰り返しなど）だけ、そちらにする。全体像の節には、全体の関係を描く全体の図を置く。ほかの図は、問いの答えを置く節（「この文書が答える問い」のリンク先）に置く。図ごとに、答える問い、出す概念と関係（その問いに要らないものは、それが答えになる問いの図に回す）、見た目の手段（囲み・位置・並べ方・重なり・線・大きさ）ごとに表す関係の意味を書く。図に出す部品と関係のうち、説明の文書が未決・未確認の印を付けたものは、確かなものと描き分ける。
   完了条件: どの問いにも形がある。全体像の節に全体の図の案がある。どの図にも、答える問いが 1 つと、出す概念と関係の一覧と、見た目の手段ごとの意味がある。答えに関係が出る問いのうち決定表・表・文にしたものには、試した図の案と、それが遅い理由の 1 文がある。
2. `plannotator-effective-html:html` skill を Skill tool で呼び、html が指す `design-artifact` の SKILL.md を読む。読み手・対象・使い道から design-artifact の「Process」の design plan（調子、色の役割、書体の役割、配置の考え）を決めて presentation.md の「デザイン」に書き、それと説明の文書の見出しと本文と、1 の見せ方に従って HTML を作る。`h2` と `h3` は説明の文書の `##` と `###` と同じにし、`####` は `h4` にする。見出しの言葉が本文の条件と逆に読めるときだけ言い換え、報告に挙げる。HTML は次を満たす。
   - 冒頭で、対象が何をするかと全体像が分かり、中心の概念の定義に読み手が最初に会う場所で会える。説明の文書の題の直後の箇条は作り手への入力なので、HTML には元の資料の名前と版（リポジトリと commit、ページと版）だけを出典として載せ、読み手と使い道、頼まれた内容、手元の絶対パスは載せない。
   - 目次から節へ飛べ、値・条件・例外・失敗したときの挙動を見出しから探せる。参照の節の値と一覧は、表か折りたたみで、本文の流れを切らずに確かめられる。
   - 確かな事実と、推論・未確認・未決が見分けられる。食い違いと確かめられなかったことは 1 つの節に集め、本文の該当の箇所から印で指す。
   - 大事な主張の出典を、読み手が元の資料を開いて辿れる形（パスと行、ページの節の名前）で示す。作業メモの番号は出典に使わず、元の資料の位置で書く。
   - 1 枚のページをスクロールで読む形で、スライドの切り替えや順に出す演出を使わない。
   - 見た目の強さを、構成の階層の順（`h2`、`h3`、見出しの直後の答えの文、本文、注釈と出典）に合わせ、どの要素も自分を含む見出しより強く見せない。まとまりは見出しの前を後より広くあけた余白で表し、囲みは包含か 1 つのまとまりを表すときだけ使う。
   - 日本語の本文の 1 行は全角 40 字前後までにする（W3C JLReq 2.4.2。plugin の 65 字は欧文の数）。
   - 図の文字とコードは、どの画面幅でも、描画した大きさで注釈の文字より小さくしない。図が答える問いと凡例は図の直前か直後に置き、線や箱には凡例でなく直接ラベルを付ける。複雑な図は、図の関係を文か表でも読めるようにする。狭い幅で図を容れ物の中でスクロールさせるときは、続きがあると分かる手がかりを付ける。
   - 狭い幅か文字の拡大で横にスクロールする図・表・コード（`pre`）の容れ物は、キーボードで中身を辿れるようにする。中に Tab で選べる要素がない容れ物は、ブラウザが自動でフォーカスするかに頼らず、容れ物を Tab で選べるようにする（`tabindex="0"`）。
   - 読み手が解説をまたいで覚える部品は、解説が替わっても同じ形にする: 確かさの印は語（「推論」「未確認」「未決」「食い違い」）で示して色は補助にし、目次はどの画面幅でも `h1` より前に出さず、長いページではどの節からも目次へ戻れるようにし、本文の中の節の参照はリンクにし、出典は本文より弱い見た目で文の流れを切らない位置（文末か段落のあと）に置く。ほかの見た目（色・書体・図の描き方）は対象に合わせて plugin に任せる。

   完了条件: presentation.md の「デザイン」に、design plan と、それぞれを読み手と対象から選んだ理由がある。`index.html` が self-contained の 1 ファイルで、外部の CDN・フォント・スクリプトを読み込まない。
3. HTML を描画して確かめて直す。描画した結果で、console のエラー、`h2` と `h3` が説明の文書の見出しと同じか（2 で言い換えたものを除く）、見た目で見出し・表・リストに見えるものがその意味の要素（か ARIA の役割）を持つか（1.3.1）、目次と本文のリンクが行き先の節に飛ぶか、折りたたみや切り替えなどの操作が動くかを確かめる。幅 1280（PC）、幅 320（モバイル、WCAG 2.2 の 1.4.10）、幅 640（幅 1280 の 200% の拡大、1.4.4）で、ページの本体が横にあふれないか（広い図・表・コードは自分の容れ物の中でスクロールする）、図・表・コードの端が容れ物に切られてスクロールでも見えなくなっていないか、文字が欠けないか、幅 640 で幅 1280 のときより小さくなる文字が幅 320 で幅 1280 のときの半分以上あるか（どこかの拡大で 200% に届くか）、図の文字とコードが注釈の文字より小さくないか、2 の見た目の強さの順が保たれるかを測って確かめる。ページが描くテーマ（light と dark があれば両方）ごとに、chrome-devtools-mcp の `lighthouse_audit` の accessibility を走らせ、図の文字と確かさの印のコントラストが 4.5:1 以上か（1.4.3）と、図の理解に要る線と形（同じ情報を見える文字で示していないもの）が隣の色と 3:1 以上か（1.4.11）を測る。Tab で目次・リンク・操作・横にスクロールする容れ物を順に辿り、フォーカスが見えて、固定した要素に隠れないかを確かめる（2.1.1、2.4.7、2.4.11）。`evaluate_script` で行の高さ 1.5 倍・字の間隔 0.12em・語の間隔 0.16em の `<style>` を足し、幅 1280 と 320 で、HTML と図の文字が切れず、図のラベルが囲みからはみ出さず重ならないかを確かめる（1.4.12）。図の意味と配置と、まとまりの見え方は画面写真で見る。冒頭の要約、各節の見出しの直後の文、図のラベルと線と、説明の文書になく HTML で足した主張を、説明の文書の同じ主張と出典と突き合わせ、HTML で足した主張は、主張ごとに元の資料の行を開いて確かめる（「〜がない」「決まっていない」と書く主張は、範囲を主張の中に書き、その範囲の資料を読んで確かめる。検索で当たらなかったことだけを根拠にせず、読みきれない範囲は主張から外すか「未確認」にする）。図ごとに、1 でその図に出すと決めた関係を 1 つずつ図の線・囲み・位置と突き合わせ、逆に図の線と囲みを 1 つずつ説明の文書の関係と動き（全体像の節だけでなく、部分の節の分岐と戻りも）か元の資料の行と突き合わせる（図法を変えた図も同じ）。ページの見た目の手段（囲みの種類・線種・色・印）を 1 つずつ、凡例と presentation.md に書いた意味と突き合わせ、その見た目を使ったすべての箇所が同じ意味を表しているかを確かめる。合わないところは、見せ方なら presentation.md から直す。説明の文書の誤りと欠けは、元の資料に合わせて HTML を直し、説明の文書を直してよいときは説明の文書も直し、どちらでも報告に挙げる。
   完了条件: 確かめた主張の数と、直した箇所の一覧と、説明の文書の誤りと欠けの一覧が報告にある。HTML の `h2` と `h3` が説明の文書の見出しと同じ（2 で言い換えたものを除く）で、見た目と意味の要素が食い違う見出し・表・リストが 0 で、説明の文書とも元の資料とも食い違う主張が 0 で、図に出すと決めた関係の欠けと、説明の文書の関係と動きにも元の資料にもない線と囲みが 0 で、凡例や presentation.md の意味と違う意味で使った見た目と、意味の違う 2 つ以上に共通の見た目が 0 で、console のエラーと行き先のないリンクと図の文字の重なりと切れが 0。幅 1280・320・640 のどれでも、ページの本体の横のあふれと、容れ物に切られて見えない図・表・コードと、欠けた文字と、注釈の文字より小さい図の文字とコードが 0 で、200% に届かない文字が 0。どのテーマでも、lighthouse の accessibility の失敗と、4.5:1 に満たない文字と、3:1 に満たない、理解に要る図の線と形が 0。Tab で辿れない操作と容れ物と、見えないか隠れるフォーカスが 0。文字の間隔を広げたときに切れる文字と、囲みからはみ出すか重なる図のラベルが 0。

## 制約
- 書いてよいのは、置き場所の `index.html` と作業メモの場所と、直してよいときの説明の文書だけ。
- git の commit はしない。秘密の値（トークン、鍵、アカウント番号など）と個人情報（人の名前など）を入れない。
- コマンドは sandbox の中で動かし、sandbox の外で動かさない。
- `<rubric.md の絶対パス>` は読まない（型を直すときの評価に使うため）。
- 手段を simple & easy にし、既存のツールやライブラリで済むなら作らない。
- 描画の確認は chrome-devtools-mcp（`mcp__chrome-devtools__*` のツール。ToolSearch で読み込む）で、`index.html` を `file://` で開いて行う。開けるのは `file://`・`http://localhost`・`http://127.0.0.1` だけ（ほかの URL は hook が止める）。画面幅は `emulate` の viewport で変え、画面写真は `take_screenshot` を `filePath` なしで、`lighthouse_audit` は `outputDirPath` なしで呼んで応答の中で見る（`filePath` と `outputDirPath` に書けるのは Claude Code の作業ディレクトリと OS の一時ディレクトリの下だけで、作業メモの場所には書けない）。

## 報告
- `index.html` と presentation.md のパスと、`plannotator-effective-html:html` を呼んだこと。
- design plan と、それを選んだ理由の 1 行。
- 問いごとの形とその理由の 1 行ずつ（決定表・表・文にした問いは、試した図の案も）。
- 言い換えた見出しと理由（なければ「なし」）。
- 説明の文書の誤りと欠けと、HTML と説明の文書でどう直したか（なければ「なし」）。
- 確かめた主張の数と、直した箇所。
- 新しく作ったものと、探した既存のツール、それを使わなかった理由（なければ「なし」）。
- 考えた中でいちばん simple & easy な案より複雑にしたところと、それを求める本質的な複雑さ（なければ「なし」）。
- 検討したうえで扱わないことにしたコーナーケースと、扱わない理由（なければ「なし」）。
</template>
