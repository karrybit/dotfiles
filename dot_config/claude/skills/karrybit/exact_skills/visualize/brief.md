# HTML 化の依頼の型

`SKILL.md` の 2 で、下の型の `<…>` を埋めて依頼にする。

- 型の外の文（作り方の好み、ほかの成果物への感想）は依頼に足さない。足すと、作り手が型より依頼の言葉に合わせる。

<template>
# <元の資料の名前> の説明の文書を、1 ファイルの HTML にする

## 目的
説明の文書の意味（中心の概念、関係、動き、問いごとの答え、確かさの印、出典）を変えずに、読み手が HTML で全体を掴み、必要なところだけ仕様の詳細まで確かめられるようにする。読み手と使い道と頼まれた内容は、説明の文書の題の直後の箇条にある。

## 入力
- 説明の文書: `<説明の文書の Markdown の絶対パス>`。<「直してよい」か「読むだけ」>。中心の概念と関係と動きと「この文書が答える問い」は全体像の節に、見出しのアウトラインは `##` と `###` に、元の資料の場所と版と読み方は題の直後にある。事実の洗い出しと `##` の構成はやり直さない。本文（箇条・番号つきの並び・関係の一覧）と `###` の区切りは HTML の素材で、HTML の形は 1 で決める。
- 元の資料: 説明の文書の題の直後にあるもの。説明の文書と HTML の主張を確かめるときと、説明の文書の誤りや欠けを見つけたときだけ開き、checkout・fetch・書き込みをしない。
- 置き場所: `<HTML を書き出す絶対パス>`
- 作業メモ: <scratchpad のパス>/presentation.md

## 手順
1. 読み手のタスクごとの見せ方を presentation.md の「見せ方」に書く。
   - タスク: 「この文書が答える問い」と、各節の答えの文と本文から、読み手が HTML でする理解のタスク（全体を掴む、部品の責務を引く、流れや状態の移り変わりを追う、2 つを比べる、失敗の止まる位置を探す、値を引く など）を動詞で挙げる。問いの答えの節に限らず、関係・流れ・状態・比較を持つ節はどれもタスクの元にする。
   - 見せる単位: タスクごとに、同時に見せる概念と関係（節をまたいでよい）、まとめる単位、強調するものと省くもの、詳しさ（全体・部分・値）を決める。何を同時に見せ、何を詳細に回すかは `plannotator-effective-html:html-diagram` の SKILL.md の「Choose the right model」に従う。
   - 形: 関係を持つ見せる単位は、表や文にする前に、概念と関係（もの・主体と、その間の動詞・順序・境界・対比）にまとめて図にする案を作る。図の形は、出す関係の意味（説明の文書の関係の種類）を、同じ意味を読み手が受け取る見た目に写して選ぶ: 包含と所有は内側に置く囲み、階層は入れ子か木、順序と時間は 1 本の軸の上の位置、対比と対立は同じ記法で横に並べるか軸の両端に置く、共通部分は重なり、主体と対象の組ごとに決まる関係（権限など）は行列、依存・呼び出し・因果・遷移は向きのある線、やりとりとその境界はシーケンス図。重なりは共有する要素があるときだけ、大きさと帯の幅は資料に量があるときだけ使い、ページのどの図でも、同じ意味には同じ見た目（色・線・印）を使い、意味の違う関係と印に同じ見た目を使わない。候補の図法と描き方は `plannotator-effective-html:html` の参照（`references/diagrams.md`、量があれば `references/charts-and-data.md`）に従う。資料どうしの食い違いは 2 つの形を同じ記法で並べた図に、失敗と例外は正常の流れの図の上に止まる位置を印で載せた図にする案を作る。図の案が決定表・表・文より遅く分かるとき（条件の組み合わせ、値の一覧、単純な繰り返しなど）だけ、そちらにする。
   - 置き場所: 全体像の節に全体の関係を描く全体の図を置き、その主な箱を部分の節へのリンクにし、部分の節から全体の図へ戻るリンクを置く。部品・流れ・状態の節には、全体の図のその部分を開いた図を置く。節をまたぐ関係の図は、読み手が最初にその関係を要する節に置き、ほかの節からリンクで指す。
   - 本文の形: 節ごとに、説明の文書の本文をどの形で見せるかを決める。項目どうしがつながる箇条（原因と結果、前後、包含）は、図にするか、つなぎの語を書いた段落にする。順序・因果・包含のない並列の項目は箇条か表に、値は表にする。図が描く関係は図に任せ、図の隣の本文では図にない条件と例外だけを書く。`###` の節を図か表にまとめるときは、図の見出しか表の行にし、`###` と同じ名前のアンカーを残し、`###` から行き先への対応を書く。
   - 図ごとに、助けるタスク、持ち帰りの 1 文（読み手が図から持ち帰る結論）、出す概念と関係（その図の持ち帰りに要らないものは、部分の図か表に回す）、見た目の手段（囲み・位置・並べ方・重なり・線・大きさ）ごとに表す関係の意味を書く。図に出す部品と関係のうち、説明の文書が未決・未確認の印を付けたものは、確かなものと描き分ける。
   完了条件: どのタスクにも形がある。全体像の節に全体の図の案がある。どの図にも、助けるタスクと、持ち帰りの 1 文と、出す概念と関係の一覧と、見た目の手段ごとの意味がある。関係・流れ・状態を持つ節のうち図にしなかった節には、試した図の案と、それが遅い理由の 1 文がある。どの `##` と `###` の節にも本文の形があり、図か表にまとめた `###` のどれにも行き先がある。
2. `plannotator-effective-html:html` skill を Skill tool で呼び、html が指す `design-artifact` の SKILL.md を読む。読み手・対象・使い道から design-artifact の「Process」の design plan（調子、色の役割、書体の役割、配置の考え）を決めて presentation.md の「デザイン」に書き、それと 1 の見せ方に従って、説明の文書の意味から HTML を書く。本文は 1 の本文の形で組み直して書き、説明の文書を Markdown の変換器（markdown-it など）でそのまま HTML にしない。`h2` は説明の文書の `##` と同じにし、`###` は 1 で図か表にまとめたものを除いて同じ名前の `h3` に、`####` は `h4` にする。見出しの言葉が本文の条件と逆に読めるときだけ言い換え、報告に挙げる。HTML は次を満たす。
   - 冒頭で、対象が何をするかと全体像が分かり、中心の概念の定義に読み手が最初に会う場所で会える。説明の文書の題の直後の箇条は作り手への入力なので、HTML には元の資料の名前と版（リポジトリと commit、ページと版）だけを出典として載せ、読み手と使い道、頼まれた内容、手元の絶対パスは載せない。
   - 目次から節へ飛べ、値・条件・例外・失敗したときの挙動を見出しから探せる。参照の節の値と一覧は、表か折りたたみで、本文の流れを切らずに確かめられる。
   - 確かな事実と、推論・未確認・未決が見分けられる。食い違いと確かめられなかったことは 1 つの節に集め、本文の該当の箇所から印で指す。
   - 大事な主張の出典を、読み手が元の資料を開いて辿れる形（パスと行、ページの節の名前）で示す。作業メモの番号は出典に使わず、元の資料の位置で書く。
   - 1 枚のページをスクロールで読む形で、スライドの切り替えや順に出す演出を使わない。
   - 見た目の強さを、構成の階層の順（`h2`、`h3`、見出しの直後の答えの文、本文、注釈と出典）に合わせ、どの要素も自分を含む見出しより強く見せない。まとまりは見出しの前を後より広くあけた余白で表し、囲みは包含か 1 つのまとまりを表すときだけ使う。
   - 日本語の本文の 1 行は全角 40 字前後までにする（W3C JLReq 2.4.2。plugin の 65 字は欧文の数）。
   - 図の文字とコードは、どの画面幅でも、描画した大きさで注釈の文字より小さくしない。図の持ち帰りの 1 文と凡例は図の直前か直後に置き、線や箱には凡例でなく直接ラベルを付ける。複雑な図は、図の関係を文か表でも読めるようにし、その文か表は図の説明（`figcaption` か図に付けた折りたたみ）に置く。狭い幅で図を容れ物の中でスクロールさせるときは、続きがあると分かる手がかりを付ける。
   - 狭い幅か文字の拡大で横にスクロールする図・表・コード（`pre`）の容れ物は、キーボードで中身を辿れるようにする。中に Tab で選べる要素がない容れ物は、ブラウザが自動でフォーカスするかに頼らず、容れ物を Tab で選べるようにする（`tabindex="0"`）。
   - 読み手が解説をまたいで覚える部品は、解説が替わっても同じ形にする: 確かさの印は語（「推論」「未確認」「未決」「食い違い」）で示して色は補助にし、目次はどの画面幅でも `h1` より前に出さず、長いページではどの節からも目次へ戻れるようにし、本文の中の節の参照はリンクにし、出典は本文より弱い見た目で文の流れを切らない位置（文末か段落のあと）に置く。ほかの見た目（色・書体・図の描き方）は対象に合わせて plugin に任せる。

   完了条件: presentation.md の「デザイン」に、design plan と、それぞれを読み手と対象から選んだ理由がある。置き場所の HTML が self-contained の 1 ファイルで、外部の CDN・フォント・スクリプトを読み込まない。
3. HTML を確かめて直す。3a の意味の確かめを終えてから、3b の表示の確かめをする。

   3a 意味の確かめ: HTML のソースを説明の文書と元の資料と突き合わせ、結果を presentation.md の「意味の確かめ」に書く。
   - 図: 図ごとに、1 でその図に出すと決めた関係を 1 つずつ図の線・囲み・位置と突き合わせ、「関係（説明の文書の行か元の資料の行）→ 図の要素 → 一致か不一致」の表にする（図法を変えた図も同じ）。逆向きに、図の線と囲みを 1 つずつ、説明の文書の関係と動き（全体像の節だけでなく、部分の節の分岐と戻りも）か元の資料の行と突き合わせ、表の行に足す。
   - 主張: 冒頭の要約、各節の見出しの直後の文、図のラベルを、説明の文書の同じ主張と出典と突き合わせる。説明の文書になく HTML で足した主張（図の持ち帰りの 1 文、本文を組み直して書いたつなぎの語が言う因果・前後・包含、説明の文書の関係の一覧にない図の線と囲み）は、主張ごとに元の資料の行を開いて確かめ、「足した主張 → 元の資料の行 → 扱い」の表にする。元の資料に行がない主張は、HTML から外すか「推論」の印を付ける。「〜がない」「決まっていない」と書く主張は、範囲を主張の中に書き、その範囲の資料を読んで確かめる（検索で当たらなかったことだけを根拠にせず、読みきれない範囲は主張から外すか「未確認」にする）。
   - 見た目の手段: ページの見た目の手段（囲みの種類・線種・色・印）を 1 つずつ、凡例と presentation.md に書いた意味と突き合わせ、その見た目を使ったすべての箇所が同じ意味を表しているかを確かめる。
   - 見出し: `h2` が説明の文書の `##` と同じで、`###` のどれもに同じ名前の `h3` か 1 で決めた行き先のアンカーがあるか（2 で言い換えたものを除く）を確かめる。
   - 合わないところは、見せ方なら presentation.md から直す。説明の文書の誤りと欠けは、元の資料に合わせて HTML を直し、説明の文書を直してよいときは説明の文書も直し、どちらでも報告に挙げる。

   3a の完了条件: presentation.md の「意味の確かめ」で、どの図にも関係の表があって図の線と囲みのどれもが表の行にあり、足した主張の表のどの行にも元の資料の行か、「外した」か「推論の印」の扱いがある。表に不一致が残らず、説明の文書とも元の資料とも食い違う主張が 0。HTML の `h2` が説明の文書の `##` と同じで、行き先のない `###` が 0（2 で言い換えたものを除く）で、凡例や presentation.md の意味と違う意味で使った見た目と、意味の違う 2 つ以上に共通の見た目が 0。

   3b 表示の確かめ: HTML を描画して確かめる。`plannotator-effective-html:html` の SKILL.md の「Finish the work」と `plannotator-effective-html:html-diagram` の SKILL.md の「Build and verify」の確かめを、幅 1280（PC）、幅 320（モバイル）、幅 640（幅 1280 の 200% の拡大）で行い、目次と本文のリンクが行き先の節に飛ぶかを確かめ、図の配置とまとまりの見え方を画面写真で見る。加えて、plugin が測らない次の要件を、ページが描くテーマ（light と dark があれば両方）ごとに測る。テーマごとに `lighthouse_audit` の accessibility も走らせる。直したあとは、直した要素に関わる確かめだけをやり直す。

   | 要件 | 基準 | 測り方 |
   | --- | --- | --- |
   | 見た目で見出し・表・リストに見えるものが、その意味の要素か ARIA の役割を持つ | WCAG 2.2 の 1.3.1 | ソース |
   | 図の文字と確かさの印のコントラストが 4.5:1 以上 | 1.4.3 | テーマごとに色を測る |
   | 図の理解に要る線と形（同じ情報を見える文字で示していないもの）が隣の色と 3:1 以上 | 1.4.11 | テーマごとに色を測る |
   | ページの本体が横にあふれず、広い図・表・コードは自分の容れ物の中でスクロールし、端が容れ物に切られて見えなくならない | 1.4.10 | 幅 320 |
   | 文字が欠けず、幅 640 で幅 1280 のときより小さくなる文字が幅 320 で幅 1280 のときの半分以上ある（どこかの拡大で 200% に届く） | 1.4.4 | 幅 1280・640・320 の文字の大きさ |
   | 行の高さ 1.5 倍・字の間隔 0.12em・語の間隔 0.16em・段落の後 2em で、HTML と図の文字が切れず、図のラベルが囲みからはみ出さず重ならない（日本語の段落の後と語の間隔は省いてよい） | 1.4.12 | `evaluate_script` で `<style>` を足し、幅 1280 と 320 |
   | Tab で目次・リンク・操作・横にスクロールする容れ物を順に辿れ、フォーカスが見えて固定した要素に隠れない | 2.1.1、2.4.7、2.4.11 | Tab |

   完了条件: 3a の完了条件を満たす。確かめた主張の数と、外したか推論の印を付けた足した主張の数と、直した箇所の一覧と、説明の文書の誤りと欠けの一覧が報告にある。幅 1280・320・640 のどれでも、console のエラーと行き先のないリンクと、図の文字の重なりと切れが 0。どのテーマでも、表の要件に満たない箇所と lighthouse の accessibility の失敗が 0。

## 制約
- 書いてよいのは、置き場所の HTML と作業メモの場所と、直してよいときの説明の文書だけ。
- git の commit はしない。秘密の値（トークン、鍵、アカウント番号など）と個人情報（人の名前など）を入れない。
- コマンドは sandbox の中で動かし、sandbox の外で動かさない。
- `<rubric.md の絶対パス>` は読まない（型を直すときの評価に使うため）。
- 手段を simple & easy にし、既存のツールやライブラリで済むなら作らない。
- 描画の確認は chrome-devtools-mcp（`mcp__chrome-devtools__*` のツール。ToolSearch で読み込む）で、置き場所の HTML を `file://` で開いて行う。開けるのは `file://`・`http://localhost`・`http://127.0.0.1` だけ（ほかの URL は hook が止める）。画面幅は `emulate` の viewport で変え、画面写真は `take_screenshot` を `filePath` なしで、`lighthouse_audit` は `outputDirPath` なしで呼んで応答の中で見る（`filePath` と `outputDirPath` に書けるのは Claude Code の作業ディレクトリと OS の一時ディレクトリの下だけで、作業メモの場所には書けない）。`lighthouse_audit` は `file://` では snapshot のモードで走らせ、`evaluate_script` にはファイルのパスでなく関数の本文を渡す（navigation のモードと作業メモの場所のファイルは、どちらも失敗する）。

## 報告
- 置き場所の HTML と presentation.md のパスと、`plannotator-effective-html:html` を呼んだこと。
- design plan と、それを選んだ理由の 1 行。
- タスクごとの形とその理由の 1 行ずつ（関係・流れ・状態を持つのに図にしなかった節は、試した図の案も）。
- 言い換えた見出しと理由、図か表にまとめた `###` と行き先（なければ「なし」）。
- 説明の文書の誤りと欠けと、HTML と説明の文書でどう直したか（なければ「なし」）。
- 確かめた主張の数と、足した主張のうち外したものと推論の印を付けたものの数と、直した箇所。
- 新しく作ったものと、探した既存のツール、それを使わなかった理由（なければ「なし」）。
- 考えた中でいちばん simple & easy な案より複雑にしたところと、それを求める本質的な複雑さ（なければ「なし」）。
- 検討したうえで扱わないことにしたコーナーケースと、扱わない理由（なければ「なし」）。
</template>
