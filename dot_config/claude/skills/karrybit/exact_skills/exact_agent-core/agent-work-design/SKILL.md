# 大きな仕事の作業を設計する

- この skill は、自分が引き受けた大きな仕事を、目的を外さずに調べ・決め・変え・任せ・合流させ・確かめられる Goal の集まりにする。設計した結果は、作業の地図として自分で使う。
- 良い設計は、Goal の数で測らない。要る仕事を漏らさず、本当の依存だけを残し、安全に並べ、全体として目的を満たす設計を良い設計とする。
- 依頼の用途を最初に決める。
  - 実行（既定）: 仕事そのものを頼まれた。設計したら、そのまま調べ、変え、確かめるところまで進める。
  - 計画: 計画だけを頼まれた。設計を返して止まる。
  - 指示: 別の Agent に渡す指示を頼まれた。受け手が会話を知らなくても進められる指示の全文を返す。
- 手順 3 で Goal が 1 つになったら、設計をそこでやめて、ふつうに作業する。

## 手順

1. 依頼を読み解く。目的と成功の姿（何が変われば成功か）、頼まれた範囲（調べる・決める・変える・切り替える）、確定事項（依頼者がもう決めたこと、変えてはいけない範囲）、未決定事項、制約と危険（データの消失、権限、戻せない操作、ほかの利用者への影響）を書き出す。依頼に書かれた手段は、確定した制約か、検討してよい案かを分ける。
   完了条件: 目的・成功の姿・確定事項・未決定事項・制約が、それぞれ依頼の文か調べた事実に結び付いている。
2. 現状を確かめる。最新のコード・設定・文書を読み、部品、状態の正本、共有されるファイルと環境、その持ち主を確かめる。手で読めない事実は推測で埋めず、それを確かめる調査の Goal にする。
   完了条件: 計画が頼る事実のすべてに、読んだファイルかコマンドの出力が付くか、調査の Goal が付いている。
3. 最終成果から逆算して Goal に分ける。成果物、責務、変更の理由、独立に確かめられることで区切る。調べる・変える・テストするは 1 つの Goal の中の手順にする。要らない仕事、既存の仕組みで済む仕事、終わっている仕事は Goal にしない。
   完了条件: どの Goal も 1 つの成果物と 1 つの完了の証拠を持ち、1 つの成果物を 2 つ以上の Goal が分け合っていない。
4. 依存を DAG にする。`A → B` は「A の成果か判断がないと B を正しく始められないか終えられない」ことに限る。依存ごとに種類（情報・判断・成果物・確かめと切替のゲート）と、解ける条件を書く。慣れだけで並べた順序は依存にしない。循環があれば、先に契約を決める Goal を切り出して解く。
   完了条件: どの依存にも種類と解ける条件があり、循環がない。
5. 並べ方を決める。同じファイル・設定・データ・ブランチ・環境を変える Goal の組は、DAG で独立でも競合として扱い、直列にするか、先に共有部分（契約）を 1 つの Goal で決めてから分ける。別の worktree に分けても、合流のときの競合は残る。競合も依存もない Goal は並べる。読むだけの調査は並べやすい。不確実性の大きい前提を確かめる Goal を先に置く。
   完了条件: 並べる組ごとに変える範囲が重ならない根拠があり、競合する組は直列か契約の Goal を挟み、並べた Goal の合流点と統合の担当が決まっている。
6. Goal ごとの契約を書く。入力（読むもの、待つ成果）、出力（成果物とその形）、制約（触ってよい範囲と触らない範囲）、完了の条件、停止の条件（止めて依頼者に戻す状況）を書く。呼び出し側に完了の条件の書き方や依頼の書式があれば、その形で書く。
   完了条件: どの Goal にも 5 つの項目があり、完了の条件は出力で満たしたかを示せる。
7. ゲートを置く。複数の成果が合流する所、責務・API・データの契約が決まる所、権限・所有・戻せない操作に触れる所、稼働中の環境を切り替える所、調査の結果で後の Goal が大きく変わる所の前に、レビュー・統合・切替のゲートを置く。小さく戻せて、今ある確かめで足りる所には置かない。ゲートを通っても、人の承認が要る操作（merge、公開、削除、権限の変更）の承認は、人に求める。
   完了条件: ゲートごとに、置いた理由、通る条件、止まったときに待つ Goal と進めてよい Goal がある。
8. 用途に合わせて進める。
   - 実行: 依存が解けた Goal から進める。任せるのは、任せたほうが安く確かになる Goal だけにし、その Goal の契約だけを渡す。成果を受けたら、依存する Goal に引き継ぐ。
   - 計画: 設計を返して止まる。
   - 指示: 受け手ごとに、その Goal の契約と、合流点・ゲートを含む指示の全文を返す。受け手の調査で決まることは、暫定と書く。

   完了条件: 実行では、着手した Goal がどれも依存の解けたもので、計画と指示では、実装に手を付けていない。
9. 前提が変わったら組み直す。調査、レビューの指摘、失敗で前提が変わったら、影響する Goal と依存を DAG で下流へたどり、まだ始めていない Goal の契約と依存を直し、始めた Goal への影響を確かめる。影響しない Goal は、そのまま残す。
   完了条件: 直した Goal のすべてが変わった前提から依存でたどれ、たどれない Goal は変わっていない。
10. 全体を受け入れる。Goal ごとの完了の和でなく、手順 1 の目的と成功の姿、合流後の振る舞い、残る危険で、仕事全体を確かめる。
    完了条件: 成功の姿のどれにも、確かめた出力か、確かめられなかった理由が付いている。

## 反例の点検

手順 5 と 10 の前に、次の反例を探す。見つけたら、注意書きを足すより先に、Goal の境界、依存、担当、順序を直す。

- 全部の Goal を終えても、元の問題が残る。
- 要る成果、移行、削除、横断の確かめが、どの Goal にもない。同じ責務を 2 つの Goal が持つ。
- 決まっていない判断に頼る実装を先に走らせる。依存のない Goal を直列にしている。
- 同じファイル、共有状態、環境、権限、セッションを、2 つの Goal が同時に変える。
- 消す前に、消すものを読む・使う持ち主を確かめていない。
- 受け手に、存在しない CLI、Agent、権限、資料を求めている。
- なくても結果が変わらない Goal、段階、Agent、Script、文書がある。

## 作るものと任せるもの

- Goal と依存は、返事か、呼び出し側のタスク管理の仕組みに書く。この設計のための Agent、Script、状態のファイル、計画の文書を新しく作るのは、呼び出し側の決まりが求めるときか、引き継ぎに要るときだけにする。
- この skill が決めるのは、Goal の集合、依存、並べ方、ゲート、Goal の間の契約まで。
  - Goal ごとの完了の条件を書く手順を呼び出し側が持つなら、その手順に Goal と契約を渡す。
  - 要求と設計の文書がそろった 1 つの開発の中で、インクリメントを不確実性の順に並べる計画は、開発の計画の役に任せ、その開発を 1 つの Goal として扱う。
  - 作った計画が次の工程に進めるかの判定は、独立したレビューに任せる。設計した側は、自分の設計を承認しない。
