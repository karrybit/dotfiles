    業務規則仕様を4つの直交する規約（ORM=事実の粒度 / SBVR=語彙表記と様相 /
    EARS=前提と契機 / DMN+Catala=規則間の優先）でレビューし、作成する手順。
    `disable-model-invocation: true` で明示呼び出しのみ。

    主用途は**進行中案件の既存記述のレビュー**。ユーザーストーリー・ユースケース
    には統一形式が存在せず（ICONIX / RDRA のような型はあるが遵守されない）、
    固定形式を入力要件にしない。形式は正規化の出力先であり、`consolidate` モード
    でのみ使う。3層（原文 / 正規化 / 指摘）は `~/.config/claude/CLAUDE.md` の
    Information Design 規則に対応し、lineage を保つ。活性成分は「正規化できない
    ことが欠陥である」——割り当て表を埋めさせる形が検出機構であり、観点を並べた
    チェックリストに置き換えると効果が消える。

    スクリプトは層ごとに分ける。`scan-prose.py` は原文層に当たり形式を要求せず
    報告のみ（門番にしない）。`check-spec.py` は正規化層の門番。同じ語でも層に
    よって価値が違うため検出規則を共有しない（例: 「場合」は原文層では自然な
    日本語なので検出せず、正規化層では規則のパターンが一意に決まらないため禁止）。

    「直ちに / 速やかに / 遅滞なく」は禁止しない。法制執務で即時性の順序が定まった
    法令用語であり、数値へ置き換えると意味の改変になる。原文層で legal-term として
    報告し、出典の有無を人が判断する（初版で禁止していたのは誤りだった）。

    プローブの活性成分は `review-doc-fresh-eyes` と同じで、根拠と等級はあちらの
    references/evidence-basis.md を参照する（重複させない）。ユースケースのフロー
    はあちらの「手順の文書」型へ回し、3体目のプローブにしない。「未決定」の3分類
    はプローブに渡さず統合段で行う（渡すと報告が抑制される）。第4の成果物型
    （決定表）が汎化するかは未検証のため `review-doc-fresh-eyes` は未改変。

    モードは review（既定）/ interview / consolidate。**語彙リスト作成は独立モード
    にも別skillにもしない**——3モード共通の最初の産物で、取得方法だけが違い
    （導出 / 聞き取り）、層の依存順序から外せないため。

    `interview` は一問一答の手順を持つ他の skill と重複しうるが、**依存にせず自己
    完結させる**。Claude Code に skill 間の依存機構はなく（詳細を持つ支持された方法
    は自身の references/）、このskillは明示呼び出し専用なので他の skill の同時読み
    込みは保証されない。確率的発火に依存すると、読み込まれなかった場合に手順が黙って
    劣化する。重複は受け入れ、規律を references/interview.md に書く。追加分の本体は
    4軸から導いた質問カタログ（EARS のパターン判別・様相の区別・例外の優先関係・
    未決定の3分類）。

    既存の用語集がある場所を拡張し、競合する語彙リストを作らない。2つできた時点で
    このskillが検出しようとしている乖離を自分で作ることになるため、守る制約とした。

    「直すか残すか」は規模で挙動を切り替えず、**常にリストを先に書いてから適用を
    問う**。判定は行数やファイル数ではなく**ユーザーが下す決定の数**（1つの語彙
    決定が50箇所の編集を覆うため、編集量では規模を過大に見る）。閾値10件は根拠の
    ない既定値。持ち越しは新しい仕組みを作らず既存の未決定レコード schema を器に
    使い、check-spec.py が分類とオーナーの欠落を検査する。

    `パターン` 宣言欄は廃止し、規則文のキーワードから導出する。欄を置くと同じ情報を
    2箇所に書かせ検査は照合しかできない（欄が情報を持たない）。導出にすると代わりに
    「キーワードの組合せが EARS のどのパターンにも対応しない」を検査でき、宣言との
    不一致より強い。ears-patterns.md の固定表がその導出規則そのもの。

    抑制は `許容: <コード> <理由>` で、**理由を必須**にする（理由なしは E217）。
    理由なしの抑制は穴だが理由付きは記録された判断。抑制が空振りしていれば W104。
    `--level` は入れない——形式が consolidate 限定になった時点で「下書きに緩い検査」
    の必要がなくなり、抑制が正当な例外を吸収する。ノブを増やさない判断。

    `出典` フィールドが normalization.md の lineage 要求（各レコードが原文へ辿れる）
    の受け皿。これがないと3層構成が形式側で担保されない。規則で欠けると W103
    （新規起草なら無視可）。`## 語彙` だけのファイルは正当な成果物として通り、規則が
    0件のときは未参照警告（W101）を出さない。事実型の読み下しも語彙を参照するため
    検査し（E106）、参照済みとして数える。

    規則間の優先の軸は **DMN を主、Catala を従**にした（旧 catala-default-logic.md →
    rule-priority.md）。初期に description へ「規程の落とし込み」と法令寄りの枠組みを
    書き、法令向け言語である Catala がそれと互いを補強していた。用途を訂正した後も
    出典を再検討していなかった。DMN は OMG 標準で対象領域が業務上の意思決定であり、
    プローブAが作る決定表の標準そのもので、欠陥を gap / overlap / subsumption として
    名前付きで定義する。その後 v1.3 の仕様本文を直読し、`Unique` は best practice では
    なく**規範**（SHALL default / SHALL NOT contain overlapping rules）、gap はエラー
    ではなく **null** を返す扱い、**subsumption は仕様の語ではない**（実務家解説由来）
    ことを確認して等級を分けた。DMN の `First`
    hit policy が「順序に依存しない宣言性」を理由に semi-deprecated であることは、
    本形式が記述順ではなく `例外元` の親参照で優先を表す根拠になる。Catala が残すのは
    木構造（DMN の `Priority` は出力値の平坦な順序で木ではない）と、例外が親を名指し
    するために命名が load-bearing になる点。

    出典照合の実績（PDF は `agents/scripts/pdf-cite` で本文抽出。poppler 不要）:
    ORM 白書の CSDP 7段は Table 1 と全項目一致し、「Step 1 is the most important
    stage of the CSDP」を原典で確認（従来は二次情報からの推定）。Catala 論文の
    prioritized default logic の主張は本文で確認。一方、旧 reference が逐語の
    エラー文字列として載せていた `conflict between multiple valid consequences...`
    は**論文本文に該当語が存在せず**（"conflict" の出現 0 件）、要約器経由の記述
    だった。欠陥名は DMN の標準用語に置き換え、Catala は意味論の根拠に限定した。

    review-doc-fresh-eyes による第1段（SKILL.md）＋第2段（出典照合3本）を実施し、
    **採用45件・却下4件**を反映済み（却下理由は読者の明示・正式名称の展開・並列起動の
    手段・スキャン検出カテゴリで、いずれも progressive disclosure か媒体が決めるもの）。
    第2段は却下ゼロ。主な修正:

      それらの If-Then 内使用を認め、原典自身の例が状態＋逸脱である。「複合は
      While+When のみ」を check-spec.py の E209 と selftest 2ケースに機械化して
      いた（誤った規則＋テストによる固定）。E209 を撤去し導出を分類に変え、原典形の

    - **SBVR の様相は2系列×3。** 不可能（never）と可能（sometimes）が欠落し、
      Behavioral / Definitional の2系列を1列に潰していた。MODALITY_SERIES で6種に。
      無制限の許可・可能は SBVR では規則ではなく advice（"No business rule is an
      advice."）なので、条件なしの許可・可能を E218 で検出する。
    - **同義語の方針が逆だった。** SBVR は Synonym / Synonymous Form / See を備える。
      「同義語を作らない」ではなく「代表語を1つ決め残りを登録する」。進行中案件の

    - **帰属誤り2件。** 「Rules build on facts...」は SBVR 本文になく Business Rules

    確定した設計に含まれる既知の限界: **数値パラメータ4つ**（プローブ体数・指摘上限件数・
    スキャンの語彙一覧・決定数の閾値10件）に根拠はない。合わなければ変える既定値であり、
    使用ごとに測って置き換える計画は持たない（SKILL.md「設定を変えるとき」）。

    確定に含まれないものが1つある。**決定表という成果物型を review-doc-fresh-eyes へ
    還流するか**は未決。今回のレビューはあちらの第1段・第2段テンプレートを使っており、
    **こちらのプローブA/B は実際の業務規則仕様に対して一度も走っていない**。汎化するかは
    初回の実使用で判断する。

    **初回の実使用（2026-08-07）。** 実案件の User Story issue 1件と、そのプロジェクトの
    ユビキタス言語辞書に対して `review` を走らせた。プローブAは文書だけから状態集合の穴
    （辞書が列挙する状態値では表せない状態が存在する）を検出し、プローブBは同語別義3件と
    辞書未定義語6件を返した。決定数は14で閾値10を超え、規定どおり持ち越しになった。
    決定表という型は業務規則仕様に対して機能した。

    そのとき**統合段で実装（API 契約・サーバ実装）を照合先にしてしまい、指摘の骨格が
    実装との差分に置き換わった**。上流だけで成立していた指摘のうち1件は消え（辞書側の
    記述は自己完結しており欠陥ではなかった）、最も重い1件は主張が入れ替わった。原因は
    「統合の役割は偽陽性の除去」を「実装で答え合わせする」と解釈したことで、数値パラメータ
    ではなく**照合先が無規定だった**。統合段の該当行に「除去の判断は原文と出典文書の中で
    行い、実装で答え合わせをしない」を、守る制約に「実装・コード・API契約・DBスキーマを
    照合先にしない」を追加し、動かさない点を5→6に増やした。

    **上流限定は著者の譲れない意志であり、記述の重複は意図的。** description・冒頭・非目標・
    守る制約・動かさない6点の5箇所に書いてある。守る制約の1箇所だけでは実際に守られなかった
    （line 272 まで読む前に統合段で逸脱した）ため、読み込み時に必ず目に入る位置へ上げた。
    冗長に見えても削らない。削るなら著者に確認する。
