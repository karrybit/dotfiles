# 通した例：経費精算の承認

Last checked: 2026-08-06

4層すべてを1つの小さなドメインで端から端まで通した例。**規則の書き方に迷ったらここを見る。** 途中で1つ欠陥を作り、それを直す形にしてある。直す前と後の差が、例外構造が何を防いでいるかを示す。

## 第1層：語彙（ORM / SBVR）

まず elementary fact から入る。ORM の CSDP step 1 に従い、実例を事実に分解する。

> 実例: 「田中が 8,000 円の申請を出した。出張ではないので自動承認された。」

これを分解すると `従業員 が 申請 を 提出する` と `申請 が 金額 を 持つ` の2つの事実になる。1つにまとめると（`従業員 が 金額 の 申請 を 提出する`）、金額のない申請を表せなくなる。**分解して意味が失われないなら、まだ elementary ではない。**

```markdown
## 語彙

### 経費精算システム

- 種別: 実体
- 定義: 経費の申請と承認を扱うシステム。規則の主体となる。

### 申請

- 種別: 実体
- 定義: 従業員が経費の支払いを求めて提出する記録。

### 従業員

- 種別: 実体
- 定義: 申請を提出する権限を持つ在籍者。

### 申請金額

- 種別: 値
- 定義: 申請が支払いを求める金額。

### 出張

- 種別: 実体
- 定義: 就業地を離れて行う業務。申請に紐づく。

### 上長

- 種別: 事実型
- 定義: 従業員が別の従業員を直属で管理する関係。
- 事実型: [従業員] は [従業員] を 直属の上長として 持つ

### 経理部

- 種別: 実体
- 定義: 経費の妥当性を審査する部門。

### 承認者

- 種別: 実体
- 定義: 申請を承認する権限を持つ従業員または部門。上長と経理部が該当する。

### 電子帳簿保存機能

- 種別: 実体
- 定義: 証憑を電子形式で法定期間保持する機能。構成により有無が変わる。

### 月次締め処理

- 種別: 実体
- 定義: 会計期間を締めるために実行される一括処理。
```

`承認者` は `上長` と `経理部` の両方を指すために置いた。これを置かないと BR-EXP-040 が「上長または経理部が応答しないとき」と書かれ、承認者が増えるたびに規則文を直すことになる。**語彙で吸収できる変化を規則文に持ち込まない。**

## 第2層：規則文（EARS）

キーワードは日本語の固定形を使う。対応は `references/ears-patterns.md`。

```markdown
## 規則

### BR-EXP-010 上長承認の原則

- 例外元: なし
- 出典: 経費規程 第8条
- 規則: [経費精算システム] は [申請] を、その [申請] を提出した [従業員] の [上長] の承認対象と しなければならない

### BR-EXP-060 承認時の会計連携

- 例外元: なし
- 出典: US-1180 受入基準
- 規則: [申請] が 承認されたとき、[経費精算システム] は 会計システムへ 仕訳を 送信 しなければならない

### BR-EXP-050 証憑の保持

- 例外元: なし
- 出典: 電子帳簿保存法対応方針 v2
- 規則: [電子帳簿保存機能] を備える構成では、[経費精算システム] は [申請] の証憑を 7年間 保持 しなければならない

### BR-EXP-040 承認者不在時の差戻し

- 例外元: なし
- 出典: US-1355 代替フロー
- 規則: [承認者] が 30日 以上 応答しない ことが 発生したならば、[経費精算システム] は [申請] を [従業員] に 差戻し しなければならない

### BR-EXP-070 月次締め中の受付保留

- 例外元: なし
- 出典: 経理運用手順 3.2
- 規則: [月次締め処理] が実行中である間、[申請] が 提出されたとき、[経費精算システム] は 受付を 保留 しなければならない
```

パターンを書く欄はない。上の5件は順に **常時 / 契機 / 構成 / 逸脱 / 複合** と導出される（`references/spec-format.md`）。検査結果に内訳が出るので、意図と違えば規則文を直す。

## 第3層：命名（例外構造が要求する前提）

上の5件はすべて例外を持たない。ここに例外を足す段で、**命名がなければ例外を書けない**ことがわかる。

```
- 例外元: BR-EXP-010 ← 参照先に名前がなければこの行が書けない
```

だから ID は装飾ではない。ID を持たない規則は例外の対象になれず、原則と例外の構造そのものが表現できない。

## 第4層：例外構造（DMN / Catala）— まず欠陥のある版

少額の自動承認と、出張の経理承認を足す。素直に書くと両方が原則の例外になる。

```markdown
### BR-EXP-020 少額申請の自動承認

- 例外元: BR-EXP-010
- 出典: US-1101 受入基準
- 規則: [申請] の [申請金額] が 10,000円 以下 である間、[経費精算システム] は [申請] を 自動承認 しなければならない

### BR-EXP-030 出張申請の経理承認

- 例外元: BR-EXP-010
- 出典: US-1240
- 規則: [申請] が [出張] に 紐づく 間、[経費精算システム] は [申請] を [経理部] の承認対象と しなければならない
```

**第0段のスクリプトはこれを通す。** 形式は正しい。壊れているのは意味であり、そこはプローブAが決定表を作って見つける。

`出典` が2件で別のチケットを指していることに注意。**この2行はもともと別のストーリーに書かれていた。** 散在していた規則を集約した結果、衝突が初めて可視化されている。

| 申請金額 | 出張 | 適用される規則 | 帰結 |
| --- | --- | --- | --- |
| 8,000円 | なし | BR-EXP-020 | 自動承認 |
| 50,000円 | あり | BR-EXP-030 | 経理部が承認 |
| 50,000円 | なし | BR-EXP-010 | 上長が承認 |
| **8,000円** | **あり** | **BR-EXP-020 と BR-EXP-030** | **決定できない** |

最後の行が DMN のいう **overlap**（重複）である。BR-EXP-020 と BR-EXP-030 は同じ親の兄弟であり、条件が重なるのに優先が決まっていない。

## 直した版

兄弟をやめ、片方をもう片方の例外にする。「出張なら少額でも経理が見る」という業務判断を、木の形で表す。

```markdown
### BR-EXP-020 少額申請の自動承認

- 例外元: BR-EXP-010
- 出典: US-1101 受入基準
- 規則: [申請] の [申請金額] が 10,000円 以下 である間、[経費精算システム] は [申請] を 自動承認 しなければならない

### BR-EXP-030 出張申請の経理承認

- 例外元: BR-EXP-020
- 出典: US-1240
- 規則: [申請] が [出張] に 紐づく 間、[経費精算システム] は [申請] を [経理部] の承認対象と しなければならない
```

変えたのは `例外元` の1行だけ。木はこうなる。

```
BR-EXP-010 上長承認（原則）
└── BR-EXP-020 少額なら自動承認
    └── BR-EXP-030 ただし出張なら経理承認
```

| 申請金額 | 出張 | 帰結 |
| --- | --- | --- |
| 8,000円 | あり | 経理部が承認（030 が 020 に優先） |
| 8,000円 | なし | 自動承認（020） |
| 50,000円 | あり | 経理部が承認（030） |
| 50,000円 | なし | 上長が承認（010） |

4通りすべてが1つに決まった。**この表が埋まることが、例外構造が正しいことの検査になる。**

なお 50,000円かつ出張 が 030 に落ちるのは、030 の条件が金額に触れていないため。これを意図しないなら 030 の条件を狭める。木の形は業務判断を表しており、機械的に決まるものではない。

## 未決定の3分類

```markdown
## 未決定

### UD-001

- 分類: 未決定
- オーナー: 経理部長
- 対象: BR-EXP-030
- 内容: 海外出張を国内出張と同じ承認経路にするかが決まっていない。異なるなら BR-EXP-030 の例外を足す。

### UD-002

- 分類: 書き忘れ
- オーナー: 仕様作成者
- 対象: 語彙:申請金額
- 内容: 通貨は日本円と決まっているが定義に書かれていない。確認して定義に追記する。

### UD-003

- 分類: 意図的自由
- オーナー: 実装担当
- 対象: BR-EXP-020
- 内容: 自動承認を即時実行するかバッチ実行するかは実装に委ねる。1営業日以内に完了することのみ制約とする。
```

3つは扱いが違う。

- **UD-001（未決定）** は業務判断が存在しない。実装を止める。決める人と、決まらないと何が書けないかを書く。
- **UD-002（書き忘れ）** は判断は済んでいて記録が欠けている。聞けば埋まる。実装を止めない。
- **UD-003（意図的自由）** は欠陥ではない。ただし**誰の自由か**と**何が境界か**を書かないと、自由ではなく単なる空白になる。「1営業日以内」が境界にあたる。

分類を書かない空欄は、この3つのどれとも区別できない。だから空欄そのものを禁止し、マークを義務にする。

## 検査

```sh
python3 scripts/check-spec.py 経費精算.md
```

直した版は第0段を通り、決定表も埋まる。欠陥のある版は**第0段を通ってしまう**ため、プローブAが必要になる。この非対称が段構成の理由である。

## Practical Use

- 新しい仕様を書くときは、この例の語彙をひな型にせず、**手順だけを写す**。語彙はドメインごとに違う。
- 例外が3段以上深くなったら、木ではなく表（決定表そのもの）を正本にするほうが読みやすいことがある。深さ2を超えたら一度立ち止まる。
- 決定表が組合せ爆発するなら、条件に使っている値が多すぎる。語彙の粒度を見直す兆候。

Revalidation trigger: 日本語キーワードの固定形を変えたとき。第0段のチェックを追加したとき。
