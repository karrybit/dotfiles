# ORM（事実の粒度）

Last checked: 2026-08-06

ORM（Object-Role Modeling）は Terry Halpin らが形式化した fact-based modeling の手法。**借用するのは1つ。規則が乗る事実の粒度をどう決めるか。** 表記と様相は SBVR が担当する（`references/sbvr-vocabulary.md`）。

「ORM」は Object-Relational Mapping ではない。ここでは概念モデリング手法を指す。

## Source Summary

ORM は業務領域の情報要件を、**役割を演じるオブジェクトと、その関係**として表す。モデルは elementary fact（基本事実）の上に成り立ち、図は自然言語へ読み下せる。

**elementary fact** とは、意味を失わずにそれ以上分解できない事実。具体例から入る。

```
実例:     「田中は 1995年1月5日に 入社した」
事実型:   Person was hired on Date
```

**attribute-free**（属性を持たない）が ORM の特徴。ER 図や UML と違い、すべての基本事実を関係として扱う。属性を避けることで意味の安定性が高まり、自然言語への読み下しが容易になる。属性にするかエンティティにするかという実装寄りの判断を、概念モデルの段階に持ち込まない。

### CSDP（概念スキーマ設計手順）

7段階（白書 Table 1 を原典から直接確認）。仕様を書くうえで効くのは step 1 で、残りは制約の追加。

Halpin 自身が **「Step 1 is the most important stage of the CSDP.」** と明言している。

1. 情報の実例を elementary fact に変換し、品質を検査する
2. 事実型を描き、母集団で検査する
3. まとめられる実体型を特定する。算術的な導出に注記する
4. 一意性制約を加える。事実型の項数を検査する
5. 必須役割制約を加える。論理的な導出を検査する
6. 値・集合比較・サブタイプの制約を加える
7. 残りの制約を加え、最終検査する

**step 1 が「実例から入る」ことを要求している点が重要。** 抽象的な用語の一覧から始めるのではなく、具体的な1件の記録を分解する。

### 制約の種類

自然言語へ読み下せる形で表される。

| 制約 | 意味 |
| --- | --- |
| 一意性（uniqueness） | どの役割の組が一意か |
| 必須役割（mandatory role） | その事実型への参加が必須か |
| 値（value） | 取りうる値の範囲 |
| 集合比較（subset / equality / exclusion） | 役割間の包含・一致・排他 |
| 頻度（frequency） | 参加回数の上限下限 |
| 環（ring） | 同じ型どうしの関係の性質（非反射、非対称など） |

## 分解の判定

**分解して意味が失われないなら、まだ elementary ではない。**

```
❌ [従業員] が [申請金額] の [申請] を 提出する
   → 分解できる。分解しても意味は失われない。
      ・[従業員] は [申請] を 提出する
      ・[申請] は [申請金額] を 持つ
   → まとめたままだと「金額未入力の申請」を表せない。
```

```
✅ [従業員] は [申請] を 提出する
   → これ以上分解すると「誰が提出したか」が失われる。elementary。
```

分解の効き目は規則を書く段で出る。金額と提出を分けておけば、「金額が未入力の申請を提出できない」という規則を**別の規則として**書ける。まとめていると、その規則を書く場所がない。

## 環（ring）事実型に注意

同じ型どうしの関係は制約が漏れやすい。

```
[従業員] は [従業員] を 直属の上長として 持つ
```

この事実型には少なくとも次を確認する必要がある。

- 自分自身を上長にできるか（非反射性）→ できないなら規則にする
- 上長関係が循環しうるか → 循環すると承認経路が閉じない
- 上長が2人いてよいか（一意性）

**承認・承継・親子・参照といった業務概念はほぼ環事実型で、ここが未検査のまま仕様が通ることが多い。** 規則として書き出すか、`未決定` に立てる。

## 属性に逃げると起きること

```
❌ 申請: { 金額, 提出者, 承認者, 承認日時 }
```

一見わかりやすいが、承認者が2人になった瞬間に構造が壊れる。関係として書いてあれば、頻度制約を1から2に変えるだけで済む。

```
✅ [申請] は [従業員] によって 承認される
   （頻度制約: 1件の申請は最大1名に承認される）
```

**attribute-free は冗長さではなく、変更に対する安定性のために選ばれている。**

## Practical Use

- 語彙を作るとき、抽象的な用語一覧から始めない。**実例を1件持ってきて分解する**（CSDP step 1）。実例が出てこないドメインは、まだ仕様を書く段階にない。
- `種別: 事実型` の項目には読み下し文を必ず書く。読み下せない事実型は、役割の名前が決まっていない。
- 制約7種のうち、この仕様形式で明示的に扱うのは規則として書けるもの（一意性、必須、値、頻度、環）。集合比較とサブタイプは語彙の定義文に書く。
- EARS のどのパターンにも収まらない規則が出たら、まずここに戻る。**規則が書けない原因は、たいてい事実の粒度が粗いこと。**
