# 初見の読者による文書レビュー

書き手と同じ文脈を持つ者は、その文書が伝わるかを判定できない。文脈を持たない読み手に読ませ、**成果物を作らせて、作れなかった箇所を欠陥として挙げさせる**。

対象ファイル: `$ARGUMENTS`（未指定なら、どのファイルを見るかユーザーに確認する）

## 前提

- 会話の文脈を持たないサブエージェントを起動できること。起動できないなら、この手順を使わない。**同じセッションでの自己レビューに置き換えてはいけない。** 外部の情報を伴わない自己レビューは効果がないことが測定されている。
- 対象がファイルとして保存されていること。

## 手順

### 1. 段を決める

| 条件 | 走らせる段 |
| --- | --- |
| 常に | 第1段（初見読者） |
| 文書が一次情報（チャットログ、議事録、他文書、URL）から転記した内容を含む | 第2段（出典照合）を足す |

第2段の判定は、文書内に出典・引用・リンクがあるかを見るだけでよい。ユーザーに選ばせない。

**観点をこれ以上増やさない。** 増やすと指摘が互いに重複し、統合コストだけが増える。

### 2. 第1段: 初見読者

サブエージェントに渡すのは下のプロンプトと対象ファイルのパスだけ。**テンプレートに埋めてよいのはファイルパスだけで、他の文を加えない。**

**渡してはいけないもの**: なぜその文書を書いたか、どんな会話や調査を経たか、書き手の意図の要約。渡すと引きずられて検出が落ちる。

```
あなたはこの文書を初めて読む読者です。書かれた経緯や背景は与えられません。

対象: <ファイルの絶対パス>

## やること

1. 文書を読む。冒頭に読者と目的が書かれていれば、まずそれを引用する。書かれて
   いなければ「読者と目的が明示されていない」と記録し、推測で補わない。
2. 下の成果物 A と成果物 B を作る。
3. 作れなかった箇所を報告する。

## 成果物 A（文書の型に合わせて1つ選ぶ）

- 行動を含む文書: この文書だけを根拠に実行計画を書く。各行動の「誰が」「何を」
  「いつまでに」を埋める。埋められない欄は「文書から決定できない」と書く。
- 事実整理・調査の文書: 主張と根拠を、主張ごとに表にする。根拠が文書内にない
  主張を明示する。
- 手順の文書: 上から実行するつもりで進み、実行できない箇所を挙げる。

## 成果物 B（常に作る）

文書を先頭から順に読み、その時点で意味が確定しない語・未説明の前提・指示対象が
決まらない代名詞を、出現順に列挙する。各項目に「後で説明される」か「最後まで
説明されない」かを記す。

## リンクの扱い

リンク先や外部の資料を開かないこと。ただし次を区別する。

- リンクを開かないと文が解釈できない → 報告する
- リンク先に詳細があるだけで、文自体は読める → 報告しない（設計どおり）

## 報告のしかた

- 該当箇所（行番号または引用）／何が作れなかったか／（書ける場合のみ）どう直すか。
- 重要でないものは報告しない。0件でよい。無理に指摘を作らないこと。
- 多くても5件。影響の大きい順に並べる。
- 修正案は任意。書けないなら書かなくてよい。
- ファイルを変更しない。報告のみ。
- 追加の質問はせず、1回で完了する。
```

**成果物を作らせる形を崩さないこと。** 観点を箇条書きで並べたチェックリストに置き換えると効果が消える。

### 3. 第2段: 出典照合（条件付き）

渡すのは下のプロンプト、対象ファイル、出典の所在、出典を取得する許可。会話の経緯は渡さない。

```
あなたは文書に書かれた事実が出典と一致しているかを検証します。書かれた経緯は
与えられません。

対象: <ファイルの絶対パス>
出典: <所在。チャンネルとメッセージ ID、ファイルパス、URL など>

事実として書かれた各記述を出典と突き合わせ、次に分類する。

- 一致: 件数だけ報告する
- 不正確: 出典と食い違う。または引用の語が変わって意味が変わっている
- 過剰: 出典にないことが事実として書かれている
- 欠落: 出典にあり、かつ文書の結論を覆しうる情報が反映されていない

欠落を最も重視する。

- 会話や口頭が唯一の出典で検証できないものは「検証不能」として分けて記す。これは
  問題ではない。
- 日付・期間・時刻範囲の計算を検算する。
- ファイルを変更しない。出典側への書き込み操作もしない。読み取りのみ。
```

### 4. 統合

統合は自動化せず、本体セッションが行う。

- 各指摘を採用・却下し、**却下したものには理由を持つ**。統合の役割は発見ではなく偽陽性の除去である。
- **成果物 B で「後で説明される」に分類された項目は、意図的な引きであることがある。** 読み物として書かれた文書（記事、章、解説）では、未回収の緊張を開いておくことが設計であり欠陥ではない。ここは本体セッションが判定する。**この判断材料をサブエージェント側のプロンプトに書いてはいけない。** 書くと報告そのものが抑制され、本当の欠落も出てこなくなる。
- 書き手にしか埋められないもの（本人の予定、関係者の立場、未確定の事実）は、文書に「未確認」として残す。埋められないことを隠さない。
- 文書を直す前に、何を直すかをユーザーに示す。

## 守る制約

このセッションの残りを通じて次を守る。

- **「必ず指摘せよ」と要求しない。** 説明と修正案の両方を必須にしない。要求を足すほど、正しい記述を欠陥と誤判定する率が上がる。
- **反復させない。** 1文書につき各段1回。ラウンドを足すと真陽性はほとんど増えず偽陽性が増える。
- **サブエージェントに割り当てる能力を落とさない。** 散文の読解と曖昧性の検出は能力差が出やすい。費用を下げるなら体数を減らす。モデルを明示指定せず、セッションのものを継承させる。
- **文書規範への適合を、この手順の段にしない。** 自分が規範を見て書いたものを同じ規範で見直すのは自己レビューと同じ構造になる。とくに `japanese-tech-writing` と `cognitive-rhythm-writing` は**記述段階**の規範であり、このレビューに足さない（後者は自前の執筆後点検手順を持つ）。他人が書いた文書、または規範を変えて既存文書を洗うときだけ、別の作業として行う。
- **レビューの費用が文書の価値を超えないこと。** 私的メモに何十分もかけるなら、書き直すほうが速い。

## 設定を変えるとき

**体数・上限件数・第2段のトリガーに根拠はない。** 合わなければ変える。

根拠があって動かさないのは「成果物を作らせる」「文脈を渡さない」「反復しない」「指摘を強要しない」の4点である。ここと上を混同しないこと。

迷ったときは [references/evidence-basis.md](references/evidence-basis.md) を読む。各制約の根拠と、その根拠がどれだけ強いかが書いてある。
