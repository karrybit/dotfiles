# 経緯を消して設計として書き直す

読者は、書かれた経緯を知らずにそのコメントやドキュメントに出会う。「元々はXだったが、Yの理由でZに変えた」という物語は、書いた本人には意思決定の記録として価値があるが、後から読む者には「では今は結局何なのか」を一段掘らせるノイズになる。物語はコミットメッセージや PR 本文に置く場所がある——それは「いまこの変更をコミットする」という決定とセットになる情報だからだ。ドキュメントやコメント自体は、現状の設計を、最初からそう設計されていたかのように記述する。

対象: `$ARGUMENTS`（未指定なら、どのファイル・diff・PR を見るかユーザーに確認する）

## 前提

- 会話の文脈を持たないサブエージェントを起動できること。起動できないなら、この手順を使わない。**同じセッションでの自己判定に置き換えてはいけない。** 経緯を知っている本体セッションは、まさにその経緯を説明したくなる側であり、判定者として機能しない。
- 対象がファイルとして保存されている、または `git diff` で参照できること。

## 手順

### 1. 対象を確定する

`$ARGUMENTS` がファイルパスなら対象ファイル群、diff レンジや PR 番号なら `git diff` で変更後の内容を対象にする。対象が多いときも、検出は次段でファイルごとに独立して行う——1本のプロンプトに複数ファイルを詰め込まない。

### 2. 検出: 文脈を持たないサブエージェントに経緯を判別させる

対象ファイルごとに、会話の文脈を持たないサブエージェントを起動する。**渡すのは下のプロンプトと対象ファイルのパスだけ。** なぜこの作業を頼むか、これまでの会話でどんな変遷があったかは一切渡さない。渡すと「知っているから説明を残したくなる」バイアスがそのまま検出側にも乗り、経緯記述を経緯だと気づけなくなる。この盲目性のおかげで、このセッションが一度も見ていない他者のコードやドキュメントにも同じ手順がそのまま使える。

```
あなたはこの文書/コードを読み、記述を2種類に分類します。書かれた経緯や背景は与えられません。

対象: <ファイルの絶対パス>

## 分類する2種類

- 設計記述: 今のものが何であるか、なぜそうでなければならないかを述べている。
  例:「タイムアウトは30秒。上流APIのp99が25秒のため」
- 経緯残留: 今の状態にどう到達したかを述べている。以前の実装、変更の経緯、会話・
  レビュー・意思決定の過程、セッション固有のラベルや進行状況への言及を含む。
  例:「元々はリトライ処理をここに書いていたが、複雑になったので分離した」
  「PRでの指摘を受けて追加」「Tier2対応として」

## やること

1. ファイルを先頭から読み、経緯残留と分類できる箇所を出現順に列挙する。各箇所に
   ついて、行番号または引用と、なぜ経緯残留と判定したかを記す。
2. 各箇所について、経緯残留の内容に「なぜ今そうなっているかを理解する上で
   保存する価値がある情報」が含まれるかを判定する。含まれるなら
   「コミットメッセージ材料」として、含まれない(単なる作業ログ・馬から出た
   息のような繋ぎ)なら「保存不要」として分ける。
3. 設計記述と経緯残留の境界が曖昧な箇所(経緯の説明に見えて、実は非自明な
   制約の説明でもある)は、独立した項目として「要判断」に分類する。無理に
   どちらかに決めない。

## 報告のしかた

- 経緯残留と要判断のみ報告する。設計記述は報告しない。
- ファイルを変更しない。報告のみ。
- 追加の質問はせず、1回で完了する。
```

### 3. 統合: 採用・却下・コミットメッセージ材料の分離

統合は本体セッションが行う。

- 検出結果を1件ずつ採用・却下する。**却下したものには理由を持つ**——「これは経緯に見えるが、実は非自明な制約の説明であり設計記述として必要」など。
- 「要判断」に分類された項目は、本体セッションが設計記述か経緯残留かを決める。
- 採用した経緯残留のうち「コミットメッセージ材料」と判定されたものを集め、コミットメッセージの草案を作る。実際の `git commit` は実行しない——コミットするかどうか、いつコミットするかはユーザーの決定であり、この手順の範囲外。
- 「保存不要」と判定された経緯残留は、書き直し後の文面から単純に消える。ここだけは判断を要さない。

### 4. 書き換える

採用した各箇所について、経緯を消し、同じ情報量の設計記述に書き直す。「なぜこう変わったか」ではなく「なぜ今こうなっているか(非自明な制約がある場合のみ)」を残す。自明な理由の記述(コードを読めばわかること)は経緯とともに落としてよい。

### 5. 提示する

書き換える前に、変更点の要約(どの箇所をどう変えるか)をユーザーに示す。他者が書いた文章を書き直す操作であり、通常のコード編集より確認の重みが大きい。コミットメッセージ材料があれば、ここで草案も合わせて示す。

## 守る制約

- **検出サブエージェントに会話の文脈を渡さない。** このセッションがなぜこの依頼を受けたかは、判定に一切関係がない。関係させると、経緯を知っている側の甘さがそのまま判定に乗る。
- **文章の巧拙・文体の是正はこの手順の範囲外。** 経緯残留か設計記述かの分類だけを行う。日本語の文章規範は `japanese-tech-writing`、読み物としての緩急は `cognitive-rhythm-writing` の役割であり、混ぜない。書き直した文が多少ぎこちなくても、経緯が消えて設計記述になっていれば手順としては完了している。
- **消えた記述を無言で捨てない。** 採用した経緯残留は必ず「書き直し後の設計記述」か「コミットメッセージ材料」のどちらかに反映される。この二択に落とせない、かつ保存不要とも言えない箇所は、要判断のまま止めてユーザーに聞く。
- **`git commit` を実行しない。** この手順が生成するのはファイルの書き換えとコミットメッセージ案であり、コミットの実行はユーザー側の別の決定。
- **書き手が誰であるかを判定に持ち込まない。** ユーザー自身が書いたコード、Claude Code がこのセッションで書いたコメント、他者が書いた既存コードのいずれであっても、同じ検出プロンプトをそのまま使う。
